## 0. 分层交联方法：执行面与交互面分离

**问题**：多数 Agent 框架把模型调用、工具执行、人类交互、任务调度和证据留存揉在一个进程或一套提示词里；每个 harness 都要重复实现“怎么问人、怎么排任务、怎么证明做完”，人与人、人与 Agent、Agent 与 Agent 的信息流彼此割裂，换一个 harness 就要重做一遍。

**方法**：把系统分成两个面，并用共享对象连接：

- **执行面**（harness / 本地代理）：只负责模型、工具、执行环境和上下文组装；不实现人类交互协议，也不持有跨会话的任务账本。
- **交互面**（AIDash）：负责卡片、任务树、通道、长期记忆、证据卡和值守调度；通过 MCP 作为唯一 Agent 接口，通过 Web/REST 作为人的接口。
- **共享对象**：六类卡片、带租约的任务树、按 project/topic 划分的通道、项目级记忆、完成前必须存在的证据卡。
- **三条链路**：人与人（决策卡、交接话术、建议任务）、人与 Agent（四段式决策、任务树、记忆注入）、Agent 与 Agent（共享通道、原子认领、证据回写、值守壳轮询）。
- **执行端推进**：交互层只维护任务状态和证据，执行端按自己的配置轮询/认领并推进；平台不绑定某一种调度方式，后续可替换为推送、事件订阅或其他调度。人手动加任务后，执行端按当前配置的节奏认领执行。

**效果**：harness 可以替换而不重写协作逻辑；人的判断变成结构化、可回取的数据；多个 Agent 通过共享任务和证据协作；交互层可以独立演进和审计。

**问题**：代理需要人的判断，但不能无限期阻塞等待；聊天里的口头决定又难以在压缩上下文后保留，代理容易重复问或自行猜测。

**方法**：提供“提问卡”入口，要求写清背景、目标、调查参考和决策项；选项 2~10 个，每项带优点、缺点，并恰好给出一个主推荐和一个备选推荐。调用只做有界等待（例如 25 秒），无答案就返回 pending 和卡片 ID；代理记下 ID 后先去做不依赖该答案的任务，稍后按 ID 取回答案。答案按选项 ID 或自由文本落库，并出现在任务时间线上；默认动作只记录、不自动执行。

**效果**：人的决策变成结构化、异步、可回取的数据；代理不空转，也不会因为上下文丢失而反复追问。

## 2. 决策卡与任务证据闭环

**问题**：多个 AI 代理协作时，决策、执行和证据分散在不同会话里，完成后无法追溯“凭什么算完成”。

**方法**：把消息收敛为 question / info / status / artifact 等卡片类型；除 question 外，卡片必须关联 `task_id`。任务进入 done 前，必须已存在同一任务下、类型为 status 或 artifact 的证据卡；用户对卡片的已读状态按可见比例写入 `card_read`，并按任务聚合未读数。

**效果**：决策、执行、证据落在同一条任务时间线上，完成动作有可核对的凭据。

## 3. 人类长期指导的记忆化与检索注入

**问题**：人的长期约束、偏好和踩坑经验散落在历史对话里，新会话的代理看不到，容易重复犯错或重复提问。

**方法**：按项目保存 Markdown 记忆，行格式为“日期 + key + 一句话”；追加时按行去重，按 key 检索，整体替换时带期望版本号，冲突返回实际版本供合并。调用模型前，把截断后的记忆作为“历史经验，仅供参考，不是本轮指令”追加到系统提示词，并声明与任务要求冲突时以任务要求为准。汇报完成后，由学习器从汇报中提炼新的长期经验，限制条数与长度并去重。

**效果**：代理跨会话获得人的长期指导，不必重放整段历史；过期或冲突的记忆有明确的降级规则。

## 4. 值守壳/代理的任务上下文装配与证据回写

**问题**：值守壳拉起代理时，如果只传任务标题，任务描述、之前的决策、通道记忆和证据要求就丢了，代理只能重新问人。

**方法**：认领任务后，把任务字段、最近事件、关联卡片、通道/项目记忆的检索结果、完成所需的证据类型装配成任务文件或标准输入；同时在模型系统提示词中注入通道记忆。当前实现只在任务被认领后启动执行，空队列不拉起进程；后续可替换为推送等触发方式。执行结束后把状态或产物作为证据卡写回同一任务，并更新任务状态。任务文件与卡片使用稳定的任务 ID 和通道键关联。

**效果**：人的指导随任务一起到达代理；代理不必从聊天记录里猜上下文，人也能在任务树下看到执行证据。

## 5. 值守代理的通道/任务初始化与会话续接

**问题**：无人值守代理反复启动时，需要复用同一通道、避免重复建任务，并在异常中断后继续上一次 AI 会话，减少上下文浪费。

**方法**：启动时用精确通道键执行一次幂等的通道 upsert，首次创建、之后复用；创建任务时用“通道 + 标题”生成幂等键，同通道同标题复用同一条任务。当前实现中，主循环只在认领到任务时启动执行命令，空队列不拉起进程；调度方式后续可替换。命令以 argv 数组直传，不经过 shell 字符串；对支持会话参数的 CLI，按通道持久化会话 ID：首次传入新 ID，后续任务传入续接参数；续接失败时清除旧 ID，只回退一次不带续接参数的执行。

**效果**：首次接入与后续回连使用同一组命令；不会因空队列空转拉起进程；异常中断后可继续原会话或安全回退。

## 6. 跨平台命令解析、启动失败熔断与限流退避

**问题**：本地代理在 Windows 上直接启动裸命令（如 `claude`）时，实际可执行文件是 `.cmd` 包装器，容易报 `ENOENT`；如果命令起不来还按固定间隔反复释放、重认领同一任务，会形成错误风暴并触发服务端限流。

**方法**：启动前按 `PATHEXT` 解析真实可执行文件（`.exe/.com/.cmd/.bat`）；`.cmd/.bat` 经系统命令解释器执行，参数按数组逐项转义，调用方不需要处理 shell 引号。命令完全未启动（`ENOENT/EACCES`）时只释放当前任务一次，并以配置错误停止实例；服务端返回限流时读取 `retry_after` 做有界退避（例如 5~300 秒）；空闲轮询与任务间隔分别配置（默认 5 秒 / 2 秒）。

**效果**：同一套 argv 配置可跨平台运行；启动错误快速失败而不是刷屏；限流时自动降速，不把服务端打满。

## 7. 任务暂缓、隐患与结束通知覆盖层

**问题**：任务状态只有 pending/done 等主状态，无法表达“已知但先不做”“带隐患完成”“结束但用户还没看到”。

**方法**：在主状态之上增加三个覆盖层：`defer` 记录暂缓原因与计划恢复时间，不改变 status；`risk` 记录隐患说明、标记时间、解除时间与复盘结论，任何状态（含终态）都可用；结束通知用 `end_notice_read_at` 记录用户是否已确认终态。覆盖层变化写事件与审计，认领或终态不误清隐患历史。

**效果**：不伪造主状态也能表达“暂不处理”“带病完成”“尚未确认结束”，复盘时能看到当时的取舍。

## 8. 带租约与幂等键的任务认领

**问题**：多个值守进程竞争同一任务时容易重复执行；进程崩溃后任务可能永久悬挂。

**方法**：`claim` 返回带过期时间的 `claim_token`；后续 start / block / complete 等状态事件必须携带该 token。租约到期后，后台把 claimed / in_progress / blocked 的任务回收为 pending，允许其他执行者接管。创建任务支持幂等键，且按通道隔离，避免跨通道复用同一个键。

**效果**：同一任务同一时刻只被一个执行者持有；崩溃后可通过租约回收恢复，重复提交不会产生重复任务。

## 9. 汇报批次执行与素材抽取

**问题**：周期汇报需要按日/周/月/季/半年/年逐条生成，单条失败不应拖垮整批，且模型偶发空响应会让批次停在失败。

**方法**：用批次执行器统一推进状态、检查取消、执行条目和收尾；每条开始前与模型返回后各检查一次取消，失败即停止后续条目。素材从已持久化的任务、卡片、通道、执行者记录中抽取并抽样。模型返回空内容时，由调用方声明的重试次数决定是否重试；若结束原因为长度截断，重试时提高输出预算。失败时保留上一版正文，不把半成品写成成功。

**效果**：批次状态与取消语义一致；单条失败可定位；空响应不再直接终止整批。

## 10. 配置分层合并与覆盖提示

**问题**：同一配置项可能来自页面设置、环境变量、配置文件；多层覆盖时，用户不知道哪一层真正生效。

**方法**：按“页面设置 > 环境变量 > 配置文件 > 内置默认”合并。页面值存在时优先；页面把值清空时，同一进程内立即回退到下一层，不需要重启。接口返回 `env_overrides`，只列出被页面值覆盖的环境变量名，不返回值；令牌、端口、库路径等没有页面入口的键仍按“环境变量 > 配置文件 > 默认”解析。

**效果**：页面修改即时生效，同时能解释“为什么改环境变量没反应”，避免配置文件、环境变量与页面值互相打架。

## 11. 卡片列表的按需投影

**问题**：卡片列表一页可能包含大量正文与背景字段，列表页并不需要全部内容，全量读取会放大内存与响应体。

**方法**：列表查询使用显式列投影；默认把正文、背景、目标、调研、决策、消息等重字段置空，只返回从正文/背景/目标中提取并截断的 `preview_md`。需要完整正文的调用方显式传 `include_body`；单卡详情始终返回完整字段。

**效果**：高频列表请求只传摘要，详情路径保持完整；调用方按需选择，避免“一刀切”破坏现有页面。

## 12. 大目录 Markdown 渐进式索引

**问题**：一次性同步扫描数千篇文档会长时间占住事件循环，导致同一进程的 API 与 MCP 请求排队。

**方法**：用异步文件读取按批处理，每处理若干篇让出一次事件循环；每篇文档独立事务写入全文索引。索引过程接受中止信号，关机时可尽快停止；索引状态通过 `stats` 暴露“正在索引”和最近一次汇总，磁盘上消失的文档在扫描结束后从索引删除。

**效果**：大库重建期间服务仍可响应；关机不会把索引写一半；索引进度和结果可观测。
