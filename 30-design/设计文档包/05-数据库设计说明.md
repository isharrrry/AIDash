# 05 — 数据库设计说明

**文档包**：AIDash 设计文档包 V2.0
**版本**：V2.0
**日期**：2026-10-23
**上游**：`30-design/概要设计.md` §7、`03-软件设计说明.md` §5

## 0. 范围与原则

本文件定义 AIDash 的**唯一持久化层**：SQLite 单文件、18 张表、索引、约束、触发器、迁移与备份。

四条原则：

1. **单文件、零运维**：一个 `.db` 文件即全部业务数据；备份即复制 + 校验。
2. **短事务、单写者**：所有写路径必须短；禁止在事务内做 LLM/HTTP/文件 IO。
3. **事件可追溯**：卡片与任务各有一张只追加的事件表；审计表独立且不可改删。
4. **只归档不删除**：业务记录到期只改状态，不物理删除（NF-015）。

---

## 1. 数据库约定

| 项 | 约定 |
|---|---|
| 引擎 | SQLite ≥3.45（需支持 FTS5、部分索引、`RETURNING` 可选） |
| 日志模式 | `WAL` |
| 外键 | `PRAGMA foreign_keys = ON` |
| 锁等待 | `PRAGMA busy_timeout = 5000` |
| 同步级别 | `PRAGMA synchronous = NORMAL` |
| 时间 | 整数毫秒（Unix epoch ms）；对外 ISO 8601 |
| 布尔 | `INTEGER` 0/1，带 `CHECK (col IN (0,1))` |
| 结构化字段 | `TEXT` 存 JSON（`*_json`），应用层负责 schema 校验 |
| 枚举 | `CHECK (col IN (...))`，与 03 §4.4 状态机一致 |
| 主键 | 业务表用 `TEXT`（`ch_`/`cd_`/`tk_` + ULID）；事件表用自增整数 |
| 命名 | 表名单数 snake_case；字段 snake_case |
| 空值 | 可选字段允许 NULL；必填字段 `NOT NULL` |
| 字符集 | UTF-8 |

**为什么时间用整数毫秒**：避免时区字符串解析歧义与排序成本；所有比较都是整数比较，索引友好（R-016）。

**为什么结构化字段用 JSON**：卡片六种类型的可选字段差异大，拆成 6 张表会导致大量 LEFT JOIN 与稀疏列；JSON + 应用层 zod 校验在单用户规模下更简单，且 FTS 只索引真正需要检索的列。

## 2. 关系概览

```mermaid
flowchart LR
    CH["channel"] -->|"1 : n"| CA["card"]
    CA -->|"1 : n"| CE["card_event"]
    CA -->|"1 : 0..1"| CR["card_read（已读时间）"]
    CA -->|"1 : 0..1"| AR["artifact"]
    CA -->|"0..1 : 1<br/>card.task_id"| T["task"]
    T -->|"1 : n"| TE["task_event"]
    T -->|"parent_id（单父树）"| T
    T -.->|"assignee / claimed_by 存 harness_id"| H["harness（独立，无强 FK）"]
    K["kb_doc"] -->|"1 : 1（rowid 对齐）"| KF["kb_fts"]
audit_log（独立，无 FK，保留历史）
setting / schema_migration（独立）
project_memory / assistant_memory（独立，无 FK）
memory_digest_run（独立，无 FK，只追加）
report_run 记录批次 → report 存成品（逻辑 run_id，无 FK）
```

**为什么 task.assignee 不设外键**：harness 可能尚未注册就已被指派；且 harness 删除不应影响历史任务。用字符串 + 应用层校验。

**为什么 audit_log 不设外键**：审计要能在对象被归档（甚至未来被清理）后仍然可读，FK 会阻碍或产生悬空引用。

## 3. 表定义

> 迁移执行顺序见 §7；本节的排列顺序按“读起来顺”，不等于建表顺序。

### 3.1 TBL-001 `channel` — 会话通道

```sql
CREATE TABLE channel (
  id            TEXT PRIMARY KEY,
  channel_key   TEXT NOT NULL UNIQUE,
  title         TEXT,
  harness_id    TEXT,
  project       TEXT,
  topic         TEXT,
  workdir       TEXT,                 -- 002：项目根目录，≤500；旧通道可空
  status        TEXT NOT NULL DEFAULT 'active'
                CHECK (status IN ('active','archived')),
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  archived_at   INTEGER,
  last_mcp_at   INTEGER,              -- 007：最近一次 MCP tools/call 时间；判定通道在线

  CHECK (status <> 'archived' OR archived_at IS NOT NULL)
);
```

| 字段 | 说明 |
|---|---|
| `channel_key` | 业务唯一键，约定 `host/project/topic`；首次发卡自动创建 |
| `project` / `topic` | 主对话 / 子对话；从 `channel_key` 解析后物化 |
| `workdir` | 项目根目录，≤500 字符，可空；不传/传 `null` 的 upsert 不清空已有值 |
| `harness_id` | 归属 harness（可空） |
| `status` | `active` / `archived`（SM-004） |
| `last_mcp_at` | 最近一次 MCP `tools/call` 的毫秒时间；只由 MCP 入口写（读操作也写）。`agent_online = last_mcp_at 非空且 now - last_mcp_at ≤ 阈值`。不使用 `updated_at`：REST/Web 写也会刷新它，会把用户操作误算成 agent 在线。历史通道不回填 |

**索引**：

```sql
CREATE INDEX idx_channel_status_updated ON channel(status, updated_at DESC);
CREATE INDEX idx_channel_last_mcp_at ON channel(last_mcp_at);   -- 007
```

### 3.2 TBL-002 `card` — 卡片

```sql
CREATE TABLE card (
  id                TEXT PRIMARY KEY,
  channel_id        TEXT NOT NULL REFERENCES channel(id) ON DELETE RESTRICT,
  type              TEXT NOT NULL
                    CHECK (type IN ('info','handoff','question','suggestion','status','artifact')),
  status            TEXT NOT NULL DEFAULT 'open'
                    CHECK (status IN ('open','answered','dismissed','expired','archived')),
  priority          TEXT NOT NULL DEFAULT 'P2'
                    CHECK (priority IN ('P0','P1','P2','P3')),

  -- 通用内容
  title             TEXT,
  body_md           TEXT,
  background_md     TEXT,
  goal_md           TEXT,              -- 002：决策卡“达到目的或结果”
  research_md       TEXT,              -- 002：决策卡“调查参考”
  decision_md       TEXT,              -- 002：决策卡“决策项描述”
  message_md        TEXT,
  summary           TEXT,
  detail_md         TEXT,

  -- 类型专属
  severity          TEXT CHECK (severity IS NULL OR severity IN ('info','warn','critical')),
  recipient         TEXT,
  channel_kind      TEXT CHECK (channel_kind IS NULL OR channel_kind IN ('email','wechat','other')),
  reason            TEXT,
  handoff_state     TEXT CHECK (handoff_state IS NULL OR handoff_state IN ('draft','copied','sent','ack')),
  options_json      TEXT,
  allow_free_text   INTEGER NOT NULL DEFAULT 0 CHECK (allow_free_text IN (0,1)),
  default_action    TEXT,
  due_at            INTEGER,
  answer_json       TEXT,
  answered_at       INTEGER,
  artifact_url      TEXT,
  artifact_kind     TEXT,
  links_json        TEXT,

  -- 类型专属（V2.0 实现补列；不为卡片类型单独建表，表计数见 §3）
  result            TEXT CHECK (result IS NULL OR result IN ('success','failed','blocked','partial')),
  suggestions_json  TEXT,
  kb_refs_json      TEXT,
  confidence        REAL CHECK (confidence IS NULL OR (confidence >= 0 AND confidence <= 1)),
  blocking          INTEGER NOT NULL DEFAULT 0 CHECK (blocking IN (0,1)),

  -- 关联与增强
  task_id           TEXT REFERENCES task(id) ON DELETE SET NULL,
  enrichment_status TEXT NOT NULL DEFAULT 'pending'
                    CHECK (enrichment_status IN ('pending','running','done','unavailable','skipped')),
  enrichment_json   TEXT,

  -- 元数据
  idempotency_key   TEXT,
  created_by        TEXT,
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,
  archived_at       INTEGER,

  -- 类型级不变式
  CHECK (type <> 'question' OR (background_md IS NOT NULL AND options_json IS NOT NULL)),
  CHECK (type <> 'handoff'  OR (recipient IS NOT NULL AND message_md IS NOT NULL)),
  CHECK (type <> 'artifact' OR artifact_url IS NOT NULL),
  CHECK (type <> 'status' OR (summary IS NOT NULL AND result IS NOT NULL)),
  CHECK (type <> 'suggestion' OR (body_md IS NOT NULL AND suggestions_json IS NOT NULL)),
  CHECK (status <> 'answered' OR (type = 'question' AND answered_at IS NOT NULL)),
  CHECK (status <> 'expired'  OR type = 'question'),
  CHECK (status <> 'archived' OR archived_at IS NOT NULL)
);
```

| 字段 | 说明 |
|---|---|
| `background_md` / `goal_md` / `research_md` / `decision_md` | `question` 的四段：议题背景 / 达到目的或结果 / 调查参考 / 决策项描述；002 新增的三列可空以兼容历史卡 |
| `options_json` | `[{id,label,description?,pros_md?,cons_md?,recommendation_role?,recommendation?}]`；`recommendation` 为旧字段，仅兼容历史数据 |
| `answer_json` | `{option_id?, free_text?, note?, answered_by?, answered_at?}` |
| `enrichment_json` | `{analysis_md, suggestions[], kb_refs[], confidence, model, has_kb_basis, reason?}` |
| `handoff_state` | 仅 `type='handoff'`；从 `draft` 开始（SM-002 附属状态） |
| `body_md` | `info`/`suggestion` 正文；`suggestion.analysis_md` 落这一列。`status`/`handoff` 不使用该列（入口会拒绝传入），分别读 `summary`/`detail_md` 与 `message_md` |
| `summary` | `status`/`artifact` 的一句话结果 |
| `result` | 仅 `type='status'`；`success`/`failed`/`blocked`/`partial`。入口把历史 `ok`/`fail` 归一化后再落库 |
| `suggestions_json` | `[{text, rationale?, confidence?}]`；单条建议的 confidence 与整体 confidence 不同层 |
| `kb_refs_json` | `[{path, title?, excerpt?}]`，只做引用，不复制知识库正文 |
| `confidence` | `suggestion` 整体置信度，0~1；越界值在入口被拒 |
| `blocking` | `question` 是否阻塞等待（0/1）；不改变“到期只标记 expired、不替用户做决定”的约定 |

> 002 只给 `card` 追加 `goal_md`/`research_md`/`decision_md` 三个可空列，不改 001 的 CHECK：
> 历史 `question` 卡可能没有四段；**新建**卡的四段必填、选项 `pros_md`/`cons_md` 必填、
> 恰好 1 个 `primary` + 1 个 `backup`，由应用层 `shared/schemas.ts` 的 `refineQuestionOptions` 校验（见 03 §3.2.3）。

**索引**：

```sql
-- 列表与首页排序
CREATE INDEX idx_card_channel_status_priority
  ON card(channel_id, status, priority, created_at DESC);

-- 按类型筛选
CREATE INDEX idx_card_type_status ON card(type, status, created_at DESC);

-- 任务关联卡（证据查询）
CREATE INDEX idx_card_task_type ON card(task_id, type, status);

-- 幂等：同通道内唯一
CREATE UNIQUE INDEX uq_card_idem
  ON card(channel_id, idempotency_key)
  WHERE idempotency_key IS NOT NULL;

-- 过期扫描
CREATE INDEX idx_card_due ON card(type, status, due_at)
  WHERE type = 'question' AND status = 'open';
```

> 卡片搜索 `q` 用 `LIKE`（对 `%`/`_` 转义），**不建 `card_fts`**：保持本文件 18 张表的计数基线；
> 10k 卡片规模下 LIKE 足够，确有性能压力时再走迁移加索引/全文表。

### 3.4 TBL-004 `task` — 任务

```sql
CREATE TABLE task (
  id                TEXT PRIMARY KEY,
  channel_id        TEXT NOT NULL REFERENCES channel(id) ON DELETE RESTRICT,
  parent_id         TEXT REFERENCES task(id) ON DELETE RESTRICT,
  path              TEXT NOT NULL,                 -- 物化路径，如 /tk_root/tk_a/
  title             TEXT NOT NULL,
  description_md    TEXT,
  kind              TEXT NOT NULL DEFAULT 'task',   -- 004：task / suggestion
  category          TEXT,                          -- 014：单值分类（可空，空白归一为 NULL）
  end_notice_read_at INTEGER,                      -- 015：结束通知已读时间；终态时清空
  status            TEXT NOT NULL DEFAULT 'draft'
                    CHECK (status IN ('draft','pending','claimed','in_progress',
                                      'blocked','done','failed','cancelled')),
  priority          TEXT NOT NULL DEFAULT 'P2'
                    CHECK (priority IN ('P0','P1','P2','P3')),
  assignee          TEXT,                          -- harness_id，可空
  tags_json         TEXT,
  due_at            INTEGER,

  claimed_by        TEXT,
  claim_token       TEXT,
  claim_expires_at  INTEGER,
  claimed_at        INTEGER,                       -- 002：首次认领时间
  started_at        INTEGER,                       -- 001：进入 in_progress 的时间
  blocked_at        INTEGER,                       -- 002：最近一次阻塞时间
  completed_at      INTEGER,                       -- 002：完成时间
  failed_at         INTEGER,                       -- 002：失败时间
  cancelled_at      INTEGER,                       -- 002：取消时间
  blocked_reason    TEXT,
  fail_reason       TEXT,
  cancel_reason     TEXT,                          -- 003：取消原因（cancel 必填）
  defer_reason      TEXT,                          -- 008：暂缓原因；非空即“已暂缓”
  deferred_at       INTEGER,                       -- 008：最近一次暂缓时间
  deferred_until    INTEGER,                       -- 008：计划恢复时间（可选）
  risk_note         TEXT,                          -- 012：隐患说明原文
  risk_flagged_at   INTEGER,                       -- 012：最近一次标记隐患时间
  risk_resolved_at  INTEGER,                       -- 012：隐患解除时间；NULL 表示未解除
  risk_resolution   TEXT,                          -- 013：解除时的复盘结论（可选）
  evidence_json     TEXT,                          -- 证据卡 ID 数组

  idempotency_key   TEXT,
  created_by        TEXT,
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,

  CHECK (id <> parent_id),
  CHECK (status <> 'blocked' OR blocked_reason IS NOT NULL),
  CHECK (status <> 'failed'  OR fail_reason IS NOT NULL),
  CHECK (status NOT IN ('claimed','in_progress','blocked')
         OR (claim_token IS NOT NULL AND claim_expires_at IS NOT NULL)),
  CHECK (status NOT IN ('done','failed','cancelled') OR claim_token IS NULL),
  CHECK (status <> 'done' OR evidence_json IS NOT NULL)
);
```

| 字段 | 说明 |
|---|---|
| `path` | 以 `/` 开头结尾；根节点 `/tk_root/`；移动时重写子树前缀 |
| `kind` | 任务类型：`task`（普通）/ `suggestion`（建议）。枚举由入口 zod 校验；库层用默认值回填历史行，不在此加 CHECK（SQLite 的 `ADD COLUMN` 不回验旧行） |
| `category` | 单值分类（014）：≤40 字符，写入前 trim，空白字符串归一为 `NULL`；与多值 `tags_json` 分工不同（`tags` 用于检索，`category` 用于任务树成列展示）；`task.copy` 复制子树时保留 |
| `end_notice_read_at` | 结束通知已读时间（015，毫秒整数）：任务进入 `done`/`failed`/`cancelled` 时清空，表示“有一条结束提醒未确认”；用户确认后写入。`TaskView.end_notice_pending = 终态 && 该列为 NULL`。确认幂等、保留首次时间，不更新 `updated_at`；`task.copy` 生成的新草稿该列为 `NULL` 但未进入终态，因此不产生通知 |
| `claim_token` | 只在 `task.claim` 响应中返回一次；不入查询结果 |
| `evidence_json` | `["cd_x","cd_y"]`；完成时写入，用于审计复核 |
| `assignee` | 不设外键：允许先指派后注册 |
| `claimed_at` / `started_at` / `blocked_at` / `completed_at` / `failed_at` / `cancelled_at` | 状态时间线，毫秒整数；对外由 `TaskView` 转 ISO 字符串，未发生为 `null` |
| `blocked_reason` / `fail_reason` | 阻塞 / 失败原因；`blocked`、`failed` 状态下由 CHECK 保证非空 |
| `cancel_reason` | 取消原因；`cancel` 必填（003），历史行回填为固定说明 |
| `defer_reason` | 暂缓原因（008）；非空即“已暂缓”。不新增状态、不改 CHECK：`pending + defer_reason` = 没人接但已决定先不做 |
| `deferred_at` / `deferred_until` | 最近一次暂缓时间 / 计划恢复时间（毫秒整数，可空）；`claim`、`undefer` 与终态事件清空这三列 |
| `risk_note` / `risk_flagged_at` | 隐患说明与最近一次标记时间（012）；非空即“曾/正带隐患”。与 `status` 正交，任何状态可写；解除与终态**不**清空 |
| `risk_resolved_at` / `risk_resolution` | 隐患解除时间（012）与可选复盘结论（013）；`risk_resolved_at` 为 `NULL` 表示仍未解除；重新 `flag_risk` 时两列一起清空 |

> 时间线写入点与 03 §3.3 末尾的“状态时间线写入点”一致：`claim`（含过期租约接管）写
> `claimed_at`，续租不改写；`start` 写 `started_at`；`block` 写 `blocked_at` + `blocked_reason`；
> `complete`/`fail`/`cancel` 分别写 `completed_at`/`failed_at`（+ `fail_reason`）/`cancelled_at`（+ `cancel_reason`）；
> `defer` 写 `deferred_at` + `defer_reason`（+ 可选 `deferred_until`），`undefer`/`claim`/终态清空暂缓三列；
> `unblock`、`release`、租约回收都不清空历史时间列。
> 002 新增的五列可空，历史任务按 `task_event` 回填（见 §7.5）。

**索引**：

```sql
CREATE INDEX idx_task_channel_status ON task(channel_id, status, created_at DESC);
CREATE INDEX idx_task_parent          ON task(parent_id);
CREATE INDEX idx_task_path            ON task(path);
CREATE INDEX idx_task_assignee_status ON task(assignee, status);
CREATE INDEX idx_task_lease           ON task(claim_expires_at)
  WHERE status IN ('claimed','in_progress','blocked');

CREATE UNIQUE INDEX uq_task_idem
  ON task(idempotency_key)
  WHERE idempotency_key IS NOT NULL;
```

**子树查询写法**（避免 `LIKE` 的大小写与转义问题）：

```sql
-- 取某节点所有后代（不含自身）
SELECT * FROM task
WHERE channel_id = :channel_id
  AND path >= :node_path
  AND path <  :node_path || CHAR(1114111)   -- U+10FFFF，排除自身前缀
ORDER BY path;
```

> `path` 是 `TEXT`，默认 BINARY 排序；用范围比较可走 `idx_task_path`。

### 3.6 TBL-006 `artifact` — 产物引用

```sql
CREATE TABLE artifact (
  id         TEXT PRIMARY KEY,
```

**只存引用**：AIDash 不下载、不缓存、不代理制品（ADR-001）。`url` 可以是 `https://`、`file://`（本地路径）或仓库相对路径；前端只做展示与跳转。

### 3.8 TBL-008 `kb_doc` — 知识库文档元数据

```sql
CREATE TABLE kb_doc (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  path        TEXT NOT NULL UNIQUE,   -- 相对 KB 根的路径
  type        TEXT NOT NULL,          -- 来自 frontmatter，必填
  title       TEXT,
  description TEXT,
  tags_json   TEXT,
  doc_date    TEXT,                   -- frontmatter timestamp，YYYY-MM-DD
  hash        TEXT NOT NULL,          -- sha256(文件全文)
  indexed_at  INTEGER NOT NULL
);

CREATE INDEX idx_kb_doc_type ON kb_doc(type, indexed_at DESC);
```

**约束**：`path` 唯一；`type` 非空（无 `type` 的文件在索引阶段被跳过，不落库）。

### 3.9 TBL-009 `kb_fts` — 知识库全文索引

```sql
CREATE VIRTUAL TABLE kb_fts USING fts5(
  title,
  description,
  body,
  tags,
  tokenize = 'unicode61'
);
```

**rowid 对齐**：插入时显式 `rowid = kb_doc.id`，保证 `JOIN kb_doc ON kb_doc.id = kb_fts.rowid` 正确。

**中文处理（重要）**：

SQLite `unicode61` 会把连续的 CJK 字符当作一个 token（“登录设计”整体），导致搜“登录”搜不到。V2 采用**应用层逐字分词**：

```
写入：'登录设计' → '登 录 设 计'
查询：'登录'     → '"登 录"'（短语查询，保证相邻）
```

- 仅对 CJK 字符插入空格；英文/数字保持原样。
- 查询用 FTS5 短语语法（双引号）避免“登”和“录”分散命中。
- 该处理在 `kb-service` 内完成，DDL 层不感知。

**为什么不用 trigram**：`trigram` 需要 ≥3 字符，中文两字词（“登录”“部署”）无法命中；逐字 + 短语更稳。**为什么不用向量**：DQ-002 已裁决，V2 用 FTS5。
### 3.10 TBL-010 `audit_log` — 审计

```sql
CREATE TABLE audit_log (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  ts           INTEGER NOT NULL,
  actor_label  TEXT,               -- token label / harness_id / 'system'
  action       TEXT NOT NULL,      -- card.post / card.answer / task.claim / config.update ...
  object_type  TEXT,
  object_id    TEXT,
  result       TEXT NOT NULL CHECK (result IN ('ok','denied','error')),
  request_id   TEXT,
  detail_json  TEXT,               -- 只放可公开元数据
  prev_hash    TEXT,               -- 上一条的 hash
  hash         TEXT NOT NULL       -- sha256(prev_hash || 各字段)
);

CREATE INDEX idx_audit_ts            ON audit_log(ts DESC);
CREATE INDEX idx_audit_object        ON audit_log(object_type, object_id, ts DESC);
CREATE INDEX idx_audit_action        ON audit_log(action, ts DESC);
CREATE UNIQUE INDEX uq_audit_request ON audit_log(request_id)
  WHERE request_id IS NOT NULL;
```

**哈希链**：

```
hash_n = sha256(prev_hash || ts || actor_label || action || object_type
                || object_id || result || request_id || detail_json)
```

- 用途：发现“中间被删/被改”，而不是防拥有文件系统权限的人。真正的防线是 §5 的触发器与无删除 API。
- 校验命令：`aidash audit verify` 从头重算，遇到断链即报告第一个不一致的 `id`。

**不可改删触发器**：

```sql
CREATE TRIGGER trg_audit_no_update
BEFORE UPDATE ON audit_log
BEGIN
  SELECT RAISE(ABORT, 'audit_log is append-only');
END;

CREATE TRIGGER trg_audit_no_delete
BEFORE DELETE ON audit_log
BEGIN
  SELECT RAISE(ABORT, 'audit_log is append-only');
END;
```

**保留策略的边界**：审计行**永不删除**；“保留 2 年”是**最短保留期**，到期后由 `aidash export-audit` 导出到冷存储，数据库仍保留（满足 NF-015“不物理删除业务记录”与 REQ-FN-060“只追加”）。若未来确需清理，必须走独立变更单并临时移除触发器，不能在常规运维中做。

### 3.11 TBL-011 `setting` — 配置快照

```sql
CREATE TABLE setting (
  key        TEXT PRIMARY KEY,
  value_json TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

**用途**：记录“运行时被 Web 修改过的设置”，便于审计与回显。

**优先级**（与 03 §3.7.1 一致，逐键解析）：

```
页面设置（setting 表）  >  环境变量  >  配置文件  >  内置默认
```

**为什么页面值最高**：设置页保存是用户此刻的显式意图，必须立即生效且不需要重启；若环境变量始终压住它，用户会看到“保存成功但值没变”，只能去改部署配置。环境变量代表本次部署的选择，仍高于随仓库走的配置文件；从未保存过某个键时自动回退到环境变量/配置文件，清空页面值（例如 `kb_root=null`）后该键不再由页面层提供。

**提示**：同一键同时存在页面值与同名环境变量时，`GET/PATCH /api/settings` 的 `env_overrides` 返回 `[{key, env_var}]`，设置页提示“页面值覆盖了同名环境变量”。该字段只解释生效来源，不改变任何值。

**不入库的键**：`AIDASH_TOKEN`、监听地址、数据库路径、备份目录等没有页面入口，仍按“环境变量 > 配置文件 > 默认值”解析；LLM API Key 走加密文件，不在本表。

### 3.13 TBL-013 `project_memory` — 主通道记忆

```sql
CREATE TABLE project_memory (
  project    TEXT PRIMARY KEY,                 -- channel_key 的 project 段，一个主对话一份
  content_md TEXT NOT NULL DEFAULT '',         -- 整篇 Markdown：唯一真相
  version    INTEGER NOT NULL DEFAULT 1 CHECK (version >= 1),  -- 乐观锁版本
  updated_by TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

**用途**：保存某个主通道（project）跨会话、跨话题通道复用的长期约束、踩过的坑与项目偏好。agent 通过 MCP 追加行或按 key 搜行，用户在 Web 上整体编辑并预览 Markdown。

**为什么是“一整篇 + 版本号”，而不是一张行表**：

- 行表需要“行 ID 稳定”，而编辑时用户会合并/换序/重写，行 ID 很快失真，最终变成两份互相漂移的真相；
- 整篇 Markdown 与 Web 编辑器、`memory.update` 的整体替换语义天然一致，冲突用 `version` 显式暴露；
- 规模上单项目记忆上限 64,000 字符，按行搜索在内存里完成即可，不需要 FTS 或额外索引。

**写入纪律**：

| 操作 | 入口 | 并发控制 |
|---|---|---|
| 追加行（默认按行去重） | MCP `memory.append` | 事务内读-改-写 + `WHERE version = ?` |
| 整体替换 | MCP `memory.update` / REST `PUT /api/memory` | 必须带 `expected_version`，冲突返回 `MEMORY_VERSION_CONFLICT` |
| 按 key 搜行 | MCP `memory.search` | 只读 |
| 读全文 | MCP `memory.get` / REST `GET /api/memory` | 只读 |

- 内容未变化时不递增 `version`，避免“空保存”让其他终端的 `expected_version` 集体失效；
- 所有写入口都做敏感模式扫描（与卡片同一套 `assertNoSecrets`），记忆不得成为令牌的落脚点；
- 记忆只放长期有效内容，不记进度流水；超限返回 `MEMORY_TOO_LARGE`，由调用方先整理。

### 3.14 TBL-014 `card_read` — 卡片已读

```sql
CREATE TABLE card_read (
  card_id TEXT PRIMARY KEY REFERENCES card(id) ON DELETE CASCADE,
  read_at INTEGER NOT NULL
);
CREATE INDEX idx_card_read_read_at ON card_read(read_at);
```

**用途**：记录“用户已经看到过这张卡”。任务详情的信息流按 `card_id` 关联本表；任务树用“卡片存在、未归档、且本表无记录”计算 `unread_count`。

**为什么单独一张表，而不是在 `card` 上加 `read_at` 列**：

- 已读是“人”的状态，不是卡的内容。放在 `card` 上会让每次阅读都写主表、刷新 `updated_at`，把排序和增量查询一起搅乱；
- 单用户 V2 用 `card_id` 主键表达“全局已读”；将来若要多用户，只需把主键扩成 `(card_id, user_id)`，不用改 `card` 的语义；
- 外键 `ON DELETE CASCADE` 保证卡被清理时已读记录一起消失，不留下孤儿行。

**写入纪律**：

| 操作 | 入口 | 语义 |
|---|---|---|
| 标记已读 | `POST /api/cards/{id}/read` | `INSERT OR IGNORE`；重复调用保留第一次 `read_at` |
| 计算未读 | `GET /api/tasks` / `task.tree` / `task.get` | `status <> 'archived' AND task_id IS NOT NULL AND card_read.card_id IS NULL` |
| 归档 | `POST /api/cards/{id}/archive` | 不写已读；归档卡直接退出未读口径 |

**为什么已读不能只放 localStorage**：换浏览器或清缓存会让红点复活；服务端记录才能跨设备一致。前端仍保留本地 `readIds`，只用于请求成功后的即时反馈，失败时卡片保持未读。

## 5. 约束与触发器

### 5.1 完整性策略

| 层 | 负责 |
|---|---|
| 数据库 | 主键、唯一、外键、枚举 CHECK、类型级 CHECK、审计不可改删 |
| 应用 | JSON 内部结构（zod）、状态机转移、权限、敏感信息、大小限制 |
| 运维 | 备份校验、迁移校验、审计链校验 |

**为什么状态转移不写成触发器**：守卫需要读关联表（证据卡）、需要返回结构化错误码；放在 service 层更清晰，且可用单元测试覆盖。数据库只保证“状态值合法”。

### 5.2 外键与删除策略

- 全部业务外键使用 `ON DELETE RESTRICT`（`card.task_id` 用 `SET NULL`）。
- **唯一例外是 `card_read.card_id` 的 `ON DELETE CASCADE`**：已读只是卡片的派生状态，不是业务实体；卡被清理时已读记录必须一起消失，否则会留下孤儿行。它不会向外扩散——`card_read` 没有任何业务表引用它。
- 除此之外**没有任何 `CASCADE`**：防止一次误删带走整棵任务树或整个通道。
- 业务上不提供物理删除；归档改 `status`。

### 5.3 CHECK 与状态机的一致性

| CHECK | 对应规则 |
|---|---|
| `card.status IN (...)` | SM-002 |
| `task.status IN (...)` | SM-001 |
| `harness.status IN (...)` | SM-003 |
| `channel.status IN (...)` | SM-004 |
| `status <> 'answered' OR (type='question' AND answered_at IS NOT NULL)` | INV-C2/C3 |
| `status NOT IN ('claimed','in_progress','blocked') OR claim_token IS NOT NULL` | INV-T3 |
| `status NOT IN ('done','failed','cancelled') OR claim_token IS NULL` | INV-T4 |
| `status <> 'done' OR evidence_json IS NOT NULL` | INV-T5（DB 侧最小保证） |

> CHECK 只能保证“字段自洽”，不能保证“证据卡真实存在”。后者由 service 的 G-T14/G-T15 保证。

### 5.4 触发器清单

| 触发器 | 作用 |
|---|---|
| `trg_audit_no_update` | 禁止更新审计 |
| `trg_audit_no_delete` | 禁止删除审计 |

**不建** `updated_at` 自动触发器：由应用显式设置，保证同一事务内时间一致（统一时钟）。
## 6. 并发与事务

### 6.1 连接配置

```ts
// 单进程内共享一个写连接 + 一个读连接池；SQLite 的 WAL 允许读写并行
const db = new Database(config.db_path);
db.pragma('journal_mode = WAL');
db.pragma('synchronous = NORMAL');
db.pragma('busy_timeout = 5000');
db.pragma('foreign_keys = ON');
```

### 6.2 事务规则

| 规则 | 说明 |
|---|---|
| 短事务 | 目标 <50ms；禁止在事务内做 LLM/HTTP/文件 IO |
| 单一写者 | 写事务串行；应用层不需要额外锁 |
| 立即事务 | 写事务用 `BEGIN IMMEDIATE`，尽早拿写锁，减少升级死锁 |
| 重试 | `SQLITE_BUSY` 由 `busy_timeout` 吸收；仍失败 → `BUSY`（可重试） |
| 批量 | 保留策略/索引重建分批提交（每批 500 行） |

### 6.3 典型事务

```ts
// 发卡：card + event + audit 同一事务
db.transaction(() => {
  const card = cardRepo.insert(...);
  cardEventRepo.append(card.id, 'created', ctx);
  auditRepo.append('card.post', card.id, 'ok', ctx);
  return card;
}).immediate();

// 认领：单条条件 UPDATE，靠 changes() 判断
const changes = db.prepare(CLAIM_SQL).run(...).changes;
if (changes !== 1) throw new AppError('ALREADY_CLAIMED', ...);
```

### 6.4 并发压测目标

- 20 并发读 + 1 写，持续 10 分钟：`database is locked` 次数 = 0（NF-004）。
- 10 并发 `task.claim`：恰好 1 成功。
- 同一 `idempotency_key` 10 并发：只产生 1 行。

### 7.3 执行流程

```
1. 读 schema_migration 最大 version
2. 列出 migrations 中 version 更大的文件
3. 若无：结束
4. 备份当前库（§9）
5. 逐文件：校验 checksum → BEGIN IMMEDIATE → 执行 → 写 schema_migration → 更新 user_version → COMMIT
6. 任一失败：ROLLBACK 当前文件 → 恢复备份 → 报错退出（不带着半迁移启动）
```

### 7.4 迁移纪律

- 迁移文件**只增不改**；已发布的文件改一个字符都会导致 checksum 不匹配。
- 破坏性变更（删列/改类型）必须分两步：先加新列并双写，再在下一版本删旧列。
- 迁移不得依赖应用代码（纯 SQL），保证可用 `sqlite3` 手工执行。
- 每个迁移必须有对应测试：空库升级、旧库升级、失败回滚。

### 7.5 002 迁移与回填口径

`002_question_sections_and_timeline.sql` 只做可空列追加与历史数据回填，不改 001 的约束：

| 表 | 变更 | 回填 |
|---|---|---|
| `channel` | 追加 `workdir TEXT`（≤500，可空） | 不回填；旧通道保持 `NULL`，后续 `channel.upsert` 传非空值时登记 |
| `card` | 追加 `goal_md`、`research_md`、`decision_md`（均可空） | 不回填；历史 `question` 卡三列为 `NULL`，界面显示“未提供” |
| `task` | 追加 `claimed_at`、`blocked_at`、`completed_at`、`failed_at`、`cancelled_at` | 从 `task_event` 聚合回填（见下） |

任务时间回填规则（只写 `NULL` 列，不覆盖已有值）：

```sql
-- 每个任务按事件类型取最早/最近一次的时间戳，均为毫秒整数
claimed_at   = MIN(event='claimed'  的 created_at)  -- 首次认领
completed_at = MAX(event='complete' 的 created_at)
failed_at    = MAX(event='fail'     的 created_at)
cancelled_at = MAX(event='cancel'   的 created_at)
blocked_at   = MAX(event='block'    的 created_at)  -- 最近一次阻塞；unblock 不清空
```

- `claimed_at` 回填取**最早一次**认领；运行期 `claim` 写**最近一次**接手时间（续租不改写）。
- `started_at` 在 001 已存在，002 不回填；历史数据缺失时保持 `NULL`。
- 没有对应事件的历史任务，该时间列保持 `NULL`；`TaskView` 统一输出 `null`。
- 回填只读 `task_event`，不修改事件表本身（事件表只追加）。

### 7.6 015 回填口径

`015_task_end_notice.sql` 追加可空列 `task.end_notice_read_at`，并把升级前已经处于 `done` / `failed` / `cancelled` 的任务统一回填为升级时刻（毫秒）：这些任务在旧版本里没有“结束通知”概念，若保持 `NULL`，升级后整棵历史树会集体高亮。升级后新进入终态的任务才清空该列，产生一条待确认通知。

### 8.2 保留策略

| 对象 | 到期动作 | 是否删除 |
|---|---|---|
| 卡片 | `status='archived'` | 否 |
| 任务 | 不自动处理（由用户决定） | 否 |
| 事件表 | 不处理 | 否 |
| 审计 | 导出冷存储 | **否**（触发器阻止删除） |
| 日志文件 | 轮转/压缩/删除旧文件 | 是（仅文件） |

## 9. 备份与恢复

### 9.1 备份

```bash
aidash backup --out ./backups/aidash-20261023.db
```

步骤：

```
1. PRAGMA wal_checkpoint(TRUNCATE)     -- 把 WAL 落主库
2. 使用 SQLite Backup API 复制（不是直接 copy 文件，避免复制到半写状态）
3. 计算 sha256，写 aidash-20261023.db.sha256
4. （可选）gzip 压缩
```

**为什么用 Backup API**：直接复制 `.db` 在 WAL 模式下可能漏掉尚未 checkpoint 的页；Backup API 保证一致性快照。

### 9.2 恢复

```bash
aidash restore --from ./backups/aidash-20261023.db
```

步骤：

```
1. 校验 .sha256；不匹配 → 拒绝
2. 停止服务（或确认无进程占用）
3. 把当前库改名保留（aidash.db.bak-<ts>），不直接删
4. 复制备份为新库
5. 启动并检查 /health（schema 版本、可读写、KB 状态）
6. 失败：回滚到 .bak，报告原因
```

### 9.3 目标与演练

| 指标 | 目标 | 验证 |
|---|---|---|
| RPO | ≤24h | 每日自动备份 |
| RTO | ≤1h | 每季度一次恢复演练并计时 |
| 备份完整性 | 校验和匹配 | 每次备份后自动校验 |

## 10. 容量估算

按 V2 上限（100 通道 / 10,000 卡片 / 1,000 任务 / 10,000 KB 文档）估算：

| 对象 | 单条估算 | 数量 | 小计 |
|---|---|---|---|
| card（含正文，典型 2KB） | 2 KB | 10,000 | 20 MB |
| card_event | 0.2 KB | 50,000 | 10 MB |
| card_read | 0.05 KB | 10,000 | 0.5 MB |
| task | 1 KB | 1,000 | 1 MB |
| task_event | 0.2 KB | 10,000 | 2 MB |
| artifact | 0.5 KB | 5,000 | 2.5 MB |
| harness | 0.5 KB | 50 | <1 MB |
| kb_doc | 0.5 KB | 10,000 | 5 MB |
| kb_fts（含正文副本 + 索引） | ~12 KB | 10,000 | 120 MB |
| audit_log | 0.4 KB | 200,000 | 80 MB |
| 其他 | — | — | <5 MB |
| **合计** | | | **≈250 MB** |

加上 WAL（峰值约 50MB）与备份（保留 7 份，约 1.5GB），单机磁盘需求 <2GB。
