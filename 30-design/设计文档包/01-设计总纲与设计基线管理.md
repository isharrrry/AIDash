## 0. 本文件的作用

本文件是设计文档包的**总纲**，回答四个问题：

1. 这套设计文档谁说了算、冲突时听谁的（§2、§3）。
2. 编号怎么分配、怎么引用、怎么保证不重复（§4）。
3. 每条需求、每个决策、每个风险在哪里能找到（§4.1~§4.5）。
4. 设计基线怎么冻结、怎么变更（§5）。

> 阅读顺序建议：本文件 → `02-系统-子系统设计说明.md` → `03-软件设计说明.md` → `04-接口设计说明.md` → `05-数据库设计说明.md`。

## 2. 文档权威顺序（冲突时的裁决规则）

当两份文件说法不一致时，按以下顺序裁决，**上位覆盖下位**：

```
1. 20-spec/需求与验收判据文档.md            ← 需求与验收的唯一事实源
2. 30-design/概要设计.md                    ← 架构决策（ADR）与模块边界的唯一事实源
3. 30-design/设计文档包/04-接口设计说明.md   ← 字段级契约
4. 30-design/设计文档包/05-数据库设计说明.md ← 表结构契约
5. 30-design/设计文档包/06-安全性设计支撑材料.md ← 安全性要求（SAFE）唯一正文
6. 30-design/设计文档包/界面设计说明.md       ← 界面区域、属性表、交互闭环
7. 30-design/设计文档包/03-软件设计说明.md   ← 实现细节
8. 30-design/设计文档包/02-系统-子系统设计说明.md ← 系统分解说明
9. 本文件与 README                          ← 导航与索引，不承载规则
```

**三条硬规则**：

- **规则 A**：需求冲突以 `20-spec` 为准；设计不得“自行扩大需求”。
- **规则 B**：同一编号在两个文件中定义不同内容时，以**定义方**为准（见 §3 的“定义方”列），引用方必须改成引用。
- **规则 C**：任何文件不得引用已归档的 V1 文档作为当前基线；V1 只作历史参考。

**编号纪律**：

1. 编号一经分配不得复用；删除的编号留空并在变更记录中说明。
2. 一个编号只在一个文件里“定义”，其余文件只能“引用”。
3. 引用格式统一为 `前缀-编号`（如 `REQ-FN-006`、`SM-001`），不加书名号、不加空格。
4. 新增编号必须同时更新本表与 `model.json`，否则自检失败。

## 5. 设计基线管理

### 5.1 基线定义

**V2.0 设计基线**由以下文件共同构成，缺一不可：

```
20-spec/需求与验收判据文档.md
30-design/概要设计.md
30-design/设计文档包/01~05
30-design/设计文档包/README-核心包.md
30-design/model/model.json
30-design/设计文档包/checks/*.mjs
30-design/checks/三边一致.mjs
```

### 5.2 冻结与变更

| 阶段 | 允许的变更 | 需要的动作 |
|---|---|---|
| 起草中 | 任意 | 改完跑自检 |
| 待签署 | 只允许澄清性修改 | 记录到 §5.4 变更记录 |
| 已签署 | 只允许通过变更单 | 变更单 + 影响分析 + 重新签署 |

### 5.3 变更影响分析清单

任何改动必须回答：

1. 影响哪些 `REQ-FN` / `NF` / `XIF`？
2. 影响哪些 `ADR`？是否需要新增 ADR 而不是改旧 ADR？
3. 影响哪些 `MOD` / `SM` / `TBL` / `MCP`？
4. 影响哪些 `R`？是否新增风险？
5. 是否需要迁移？是否需要改验收脚本？
6. 是否需要同步 `AGENTS.md` / `skills/`（契约文件是产品的一部分）？
