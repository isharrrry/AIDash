## 0 本轮定位与边界

本轮只做两件事：**提取规格**、**给每条结论标证据等级**。

不做的事：

- 不判定“应该没问题”。没有验证手段的，一律写“需实测”。
- 不把包仓库的“当前版本”当成项目已选定的版本——它只是**锁定候选**。
- 不出最终验证意见；三类结论（可确认 / 需实测 / 不建议）留给 4B。
- 不改设计。发现设计缺口只登记，不擅自补。

> 采购需求输入：本轮**未收到独立的采购需求文档**。以下按“单用户、自用、单机部署”理解（推断），
> 若实际采购口径不同（如批量、信创、等保），本清单需重做。

## 1 证据等级定义

| 等级 | 判定标准 | 本轮用法 |
|---|---|---|
| **实测** | 本次在真实机器上执行命令并看到输出 | 只证明“这台机器 + 这个版本”，不外推到其他平台 |
| **官方文档** | 项目官方文档、包仓库元数据、许可证原文 | 本轮包版本来自 npmmirror 仓库元数据；许可证未逐项下载原文 |
| **厂商口头** | 供应商/同事转述，无书面材料 | 本轮无 |
| **推断** | 由设计约束或通用经验推出，未验证 | 必须进入待实测清单 |

**特别说明**：设计文档本身不是证据等级。它只回答“设计要求是什么”，
不回答“目标环境能不能满足”。所以每条规格都同时给“出处（哪包哪节）”与“证据等级”。

## 4 本轮实测记录（命令 + 输出）

> 以下命令均在作者本机执行，日期 2026-10-23。只证明本机，不外推。

### 4.1 工具链版本

```text
$ node --version      → v24.16.0
$ pnpm --version      → 12.4.1
$ npm --version       → 11.13.0
$ sqlite3 --version   → 未安装（命令不存在）
```

### 4.2 SQLite 内置版本

```text
$ node -e "const s=require('node:sqlite'); ... select sqlite_version()"
→ SQLite 3.53.0
```

### 4.3 WAL / FTS5 / 中文分词行为

```text
PRAGMA journal_mode=WAL            → wal
CREATE VIRTUAL TABLE ... fts5      → 成功
unicode61: MATCH '登录'            → 0 条
unicode61: MATCH '登录设计评审'    → 1 条
trigram:   MATCH '登录'            → 0 条（少于 3 字不匹配）
trigram:   MATCH '登录设'          → 1 条
trigram:   MATCH '用户登录'        → 1 条
```

**解读**：两种内置分词器都匹配不了 2 字中文查询，这正好验证了 05 §3 选择
“应用层逐字分词 + 自建索引”的必要性。trigram 只能覆盖 ≥3 字，不能替代。

### 4.4 `node:sqlite` 能力边界

```text
typeof db.backup        → undefined      ← 无 Backup API
UPDATE ... RETURNING    → 返回更新后的行 ← 支持
```

### 4.5 包仓库元数据（npmmirror，2026-10-23）

```text
vitest=5.0.5            playwright=1.64.1   esbuild=0.28.2

```

## 10 认知对齐（四问）

### ① 我理解的输入是

- **你给的**：3C2/3D/4 阶段要按 SOP 做完并检查；值守壳只走 MCP；ASCII 图改 Mermaid。
- **我推断的**：采购口径是“单用户、自用、单机”；目标机以本机 Windows 11 为参照；
  外部工单网关是独立交付物，只做边界核对，不纳入 AIDash 采购清单。
- **我实际读的**：02（部署）、03（构建与测试）、04（接口）、05（数据库）、概要设计（ADR-009/010/015）。

### ② 我的关键假设

1. “Node ≥24”是运行时下限，不代表要支持所有 24.x 小版本；候选锁 24.16.0。
2. 包仓库“当前版本”可以作为锁定候选，但必须经 §7 实测才算数。
3. 设计文档只提供约束，不提供证据；因此大量条目只能是“推断”，这不是偷懒，是事实。
4. 服务端、Web 与值守壳均已实现；2026-10-24 真实进程实测覆盖“服务能启动、CLI 能执行、
   Web 能加载 5 屏、MCP 能握手”。SEA 打包、TLS 反代、许可证原文与 SBOM 仍未实测，不冒充通过。

### ③ 我处理的歧义

| 歧义 | 处理方式 |
|---|---|
| ADR-009 写“React/Next”，未二选一 | 不擅自选；两个候选都列，进缺口 #1 |
| 4A 时 03 §1.3 曾写“三平台各构建一次”，02 只写主力机 | 平台矩阵按“未实测”处理，进缺口 #4；2026-10-24 已裁决：V1 只发 Windows，NF-009 的跨平台要求保留为后续版本目标 |
| 05 写 Backup API，但驱动未点名 | 实测 `node:sqlite` 无此 API；把冲突显式写出，交阶段 3 裁决 |
| “官方文档”用于包仓库元数据 | 明确标注来源是 npmmirror 元数据，不冒充官网文档 |
| 测试框架完全没写 | 单列 §2.5“来自经验的建议”，不混进设计约束 |

### ④ 需要你裁决的问题（1–3 个）

1. **前端选 React + Vite，还是 Next.js？** 这会影响构建、部署与依赖规模，属于设计决策，4A 不替你定。
2. **SQLite 驱动选 better-sqlite3，还是 Node 内置 `node:sqlite`？** 后者实测没有 Backup API；
   若选它，需要回阶段 3 把 05 §9 的备份方案改成 `VACUUM INTO` 并记 ADR/COR。
3. **值守壳只发 Windows，还是三平台都发？** 4A 时 03 曾写三平台，02 的部署描述只覆盖主力机；2026-10-24 已裁决：V1 只发 Windows；NF-009 的跨平台要求保留为后续版本目标。
