# 测试与质量约束

> 本文档回答三个问题：**什么算证据**、**什么条件下测试算够**、**一次改动什么时候可以合并或发版**。
>
> 它不列用例（见 [系统测试用例集.md](./系统测试用例集.md)），不记运行结果（见 [测试执行记录.md](./测试执行记录.md)），
> 不教怎么跑 E2E（见 [e2e/README.md](./e2e/README.md)）。四份文档各管一件事，同一件事不写两遍。

**本文档的地位**：[20-spec/需求与验收判据文档.md](../20-spec/需求与验收判据文档.md) 规定产品承诺什么；
本文档规定这些承诺**凭什么被相信**。一个行为在测试里是绿的、但与需求冲突，它仍然是缺陷——以需求为准。

## 1 质量目标

以下六条是不可交易的。任何一条被换掉，测试再绿也不算合格。

| # | 目标 | 谁在强制它 |
|---|---|---|
| **QO-1** | **安全边界不因方便而放松。** 令牌只从环境变量读，不进代码、夹具、提交、卡片、日志或截图；审计表只追加；知识库目录只读。 | `secret-store` / `config-log` / `unit-guards` 的负向断言，以及 CONTRIBUTING §8 |
| **QO-2** | **文档里的数字必须能复算。** 命令、路径、数字都要对得上代码或实测结果；没有测量就不写。 | [测试执行记录](./测试执行记录.md)的记录原则，README 的实测验证表 |
| **QO-3** | **未验证的不得写成已支持。** 没跑过的平台、没压过的容量、没接过的端点，一律进「未验证」清单。 | CONTRIBUTING §7、README 已知限制、本文档 §8 |
| **QO-4** | **断言用户看得见的结果，不绑实现细节。** UI 断言用页面上的可见文本，不用 CSS 选择器。 | `50-verify/e2e` 的断言方式 |
| **QO-5** | **不静默降级。** 处理不了的输入报错或给诊断，不返回空结果；已知缺陷用 `it.fails` 钉住，不删掉。 | 拒绝用例与 `report-material-branches.test.ts` 的既有做法 |
| **QO-6** | **测试全绿不等于系统无事。** 门禁覆盖不到的部分必须写出来，而不是当成不存在。 | 本文档 §2 的盲区列与 §8 |

## 2 测试层级与各自的盲区

层级按代价从低到高排列。**每一级的价值都取决于它的盲区是否写在纸上**，所以最后一列与第二列同等重要。

| 层级 | 命令 | 现状 | 能证明 | 看不见 |
|---|---|---|---|---|
| **T1 单元 / 集成** | `pnpm -C 40-build test` | **67 文件 / 596 通过 + 1 跳过** | `server` / `shared` / `cli` 的分支、状态机、错误路径、参数校验 | Web 前端渲染、真实 HTTP 往返、浏览器行为、进程生命周期 |
| **T2 值守壳自测** | `pnpm -C 40-build test:runner` | **155 项全通过** | 配置校验、匹配规则、脱敏、401 停止、JSON-RPC 错误 | 跨平台进程树、跨网络、真实 harness |
| **T3 管理台自测** | `pnpm -C 40-build manager:test` | **49 项全通过** | 管理台后端逻辑与接口 | 管理台 Web UI |
| **T4 部署脚本** | `pnpm -C 40-build test:deploy` | **2 项全通过** | 进程守卫（启停、残留判定） | 真实部署动作、真实库备份 |
| **T5 端到端** | `pnpm -C 40-build e2e` | **6 条**（2026-10-25 实测全通过） | 页面能打开、能看到预期内容、鉴权负向有效 | 写操作闭环（建卡/答卡/推进任务）、像素级视觉、非 Chromium 内核 |
| **T6 手工脚本** | `tests/manual/*.mjs` | 5 个，按需执行 | 视觉与交互细节的人工确认 | 不进 CI，无自动化兜底 |

**两个必须写明的口径：**

1. **覆盖率只统计 `10-aidash/src/server` / `shared` / `cli`**，不含 Web 前端、不含 `20-aidash-runner`、不含 `30-aidash-manager`。所以覆盖率数字不能读成「整个产品被覆盖」。具体数值以 [测试执行记录](./测试执行记录.md) 和 README 的实测验证表为准，本文档只约定范围与阈值。
2. **T1 的 1 条跳过来自平台分支**：`secret-store.test.ts` 里的 POSIX 权限用例在 Windows 上 `skipIf`。因此 POSIX 文件权限行为在本仓**没有自动化证据**，这是环境限制，不是遗漏。

## 3 证据规则

一条信息只有在「它错了会变红」时才叫证据。

### 采信

| 证据 | 为什么算 |
|---|---|
| 对操作结果做的断言 | 行为错时它会红 |
| 负向用例（错误令牌被挡、越界路径被拒） | 校验一旦放松它就红 |
| 带日期、环境、计数行的命令输出 | 别人能重跑并得到同一行 |
| 与已提交产物逐字节比对的回归 | 任何漂移都会红，包括「看起来一样」的漂移 |

### 拒斥

| 不算证据 | 为什么 |
|---|---|
| 「规则已写入」/「文件已生成」式断言 | 规则写进去但没生效时它照样绿 |
| 截图代替断言 | 不可重复、不可比对 |
| 只说「退出码 0」而不给计数行 | 退出码不携带真正重要的那个数字 |
| 从旧文档抄来的数字 | 那是记忆，不是测量 |
| 把 `skip` 当通过 | 跳过让未验证的行为看起来已被验证 |

**故意红不是噪音**：用 `it.fails` 钉住的已知缺陷必须保留，修好后改回 `it`，它就从「预期失败」变成回归守卫。删掉它比留着更糟——那等于把缺陷从记录里抹掉。

## 4 充分性

以下全部成立时，测试才算够：

1. 每条需求在 §2 的某一级有对应用例，或已在 §8 登记为未验证。**不存在第三种状态。**
2. 每个解析外部输入的地方（HTTP 请求、MCP 入参、配置文件、命令行参数、磁盘上的 JSON）除happy path 外都有拒绝用例。只有正向用例的解析器视为不存在。
3. 每条安全边界都有负向断言：令牌不出现在日志与卡片、越界路径被拒、未授权请求被挡。
4. `pnpm check` 报告的用例数等于设计的用例数减去明确跳过的那部分。不做静默扣减。
5. 新增能力的用例已登记进 [系统测试用例集](./系统测试用例集.md)，并对得上 §6 的追踪规则。

**覆盖率不是充分性标准。** 80% 的阈值是「防回退」的下限，不是「说明够好」的证明——行覆盖无法区分「断言了结果」和「执行了那一行」，而这个仓已经为此付过代价。

## 5 准入与准出

### 入口

- 依赖已按 lockfile 安装，工作区没有未解决的冲突改动；
- 测试跑的是**当前源码构建出的产物**，不是上一次的 `dist`；忘记重建等于在测昨天的代码；
- 改动若涉及设计文档，`30-design` 下的自检脚本先跑一遍。

### 准出

按顺序执行，不短路：

| 步骤 | 命令 | 通过条件 |
|---|---|---|
| 1 | `pnpm -C 40-build typecheck` | 三段 tsc（服务端 + Web + 管理台 Web）均无错误 |
| 2 | `pnpm -C 40-build test` | 零失败，且计数与本文档 §2 记录的层级一致 |
| 3 | `pnpm -C 40-build test:runner` | 零失败 |
| 4 | `pnpm -C 40-build manager:test` | 零失败 |
| 5 | `pnpm -C 40-build test:deploy` | 零失败 |

`pnpm -C 40-build check` 就是这五步的组合。顺序有理由：类型检查先于测试，避免类型错误被报成测试失败。

**两条不在 `check` 里、但发布前必须做的事：**

| 动作 | 为什么不在 check 里 | 发布前的要求 |
|---|---|---|
| `pnpm -C 40-build e2e` | 需要浏览器与动态端口，比单元测试慢一个量级，不适合每次提交 | **必须跑一次**，且 `通过 6，失败 0` |
| `pnpm -C 40-build coverage` | 耗时长，且覆盖率是周期性的成绩而非每次提交的判定 | 发版前跑一次，四项阈值（80）全部达标 |

**没有「重跑到绿」这一步。** 失败就报失败，附上失败步骤与计数行。已知不稳定的测试是缺陷，登记到 §7，不是重试规则。

## 6 需求可追踪性

### 现状

- 需求侧已闭环：**68 条功能需求 / 68 条验收准则**，每条需求都挂了验收准则 ID（见需求文档 §7.1）。
- **验收准则 → 测试用例的映射尚不存在。** [系统测试用例集](./系统测试用例集.md) 只标出了 3 条能确认的 REQ 编号，其余如实写着「没有可靠对照表」——硬填就是编。

### 规则

1. **新增能力先挂编号。** 先在 [需求文档](../20-spec/需求与验收判据文档.md) 里分配 `REQ-FN-nnn` 与验收准则，再写实现和用例。
2. **用例集必须登记新用例**，并尽量标注它守的是哪条 REQ；标不出就写明「映射待补」，不要猜。
3. **反向追踪同样成立**：一条说不出自己守哪条需求的用例，要么补上编号，要么说明它在守哪条不变量。
4. **映射表补齐前，不得声称「需求已全覆盖」。** 需求文档 §7.2 的 ACC-E2E 是一条跨组件的端到端验收设计，它证明主链路，不等于逐条需求的用例覆盖。

### 已知缺口

- MOD-011（旧工单网关）已移出本仓，**没有「不得出现旧网关痕迹」的自动化守卫**，只能靠人看。
- KB 全文检索在语法错误时退化为 `LIKE` 的分支**没有用例**。

## 7 缺陷分级

按后果定级，不按麻烦程度。

| 等级 | 定义 | 例子 |
|---|---|---|
| **致命** | 静默的错误结果，或安全边界被突破且无任何信号 | 令牌出现在日志里；审计缺一条却看不出来；越界路径被放行 |
| **严重** | 错误但可观察，或某个门禁步骤没有强制它声称的东西 | 卡片周期汇报漏素材却仍显示成功；只断言「文件被写出」的通过测试 |
| **一般** | 行为正确，但记录、文档或诊断错误或缺失 | 文档里的数字过期；错误信息无法定位 |

**缺陷与「测试全绿」不矛盾。** 现有用例没有断言到的行为出问题，测试当然是绿的；把绿当成没事，正是本文档 QO-6 要防的。

已登记的 5 条正式缺陷（D-1 ~ D-5，其中两条 HIGH）在内部缺陷台账中，不随公开仓发布；公开仓里体现为已知限制与 `it.fails`。

## 8 风险与残余

| 风险 | 影响 | 当前缓解 | 未缓解部分 |
|---|---|---|---|
| 覆盖率不含 Web 前端与 runner / manager | 前端渲染与管理台 UI 的回归没有自动化证据 | E2E 的 6 条 + 手工脚本 + T2/T3 自测 | 前端逻辑本身的行覆盖为零 |
| 只在 Chromium（Edge）验证 | Firefox / Safari 的样式与键盘交互可能不同 | 无 | 无跨内核测试 |
| `pnpm check` 不含 E2E 与覆盖率 | 提交级的门禁比发布级松 | CONTRIBUTING 要求提交前跑 `check`，发布前补 E2E | 提交时的行为回归可能漏到发布前才暴露 |
| 没有持续集成流水线 | 门禁依赖人记得跑 | `.github/workflows/release.yml` 只管发布 | 没有「push 即跑」的自动守卫 |
| POSIX 分支在 Windows 恒跳过 | 文件权限相关行为无自动化证据 | 代码按跨平台写 | 只有 Linux / macOS 上跑过才成立 |
| 手工脚本不进 CI | 视觉与交互细节无回归 | 按需执行 | 依赖人主动想起来 |
| 需求到用例无映射 | 覆盖率无法按需求计算，缺口不可量化 | 用例集按模块分组，缺口逐条列出 | 补齐映射前，只能定性判断 |

## 9 引用结构的裁剪说明

本文档的章节骨架参考了一套 GJB 质量记录包（STP / STD / STR + 型式试验 + 计量校准 + 电气安全 + 9001C 设计记录）。以下章节被整体删除，因为它们描述的是硬件交付物，对一个软件仓库没有可观测对象：

| 被删除的章节 | 为什么不适用 |
|---|---|
| 硬件环境（温湿度、供电、机柜） | 交付物是可部署的 Node 服务与 Web 前端，运行在用户的机器上 |
| 型式试验、环境应力筛选、EMC 发射与敏感度 | 没有物理实体，也没有电磁发射 |
| 计量校准、溯源链、测量不确定度 | 没有测量仪器；准确性由断言保证，不由仪器保证 |
| 电气安全、接地、绝缘耐压 | 同上 |
| 设计评审 / 验证 / 确认 / 更改记录（9001C 8.3） | 单人或小团队维护，无独立评审方；该职责由 §5 的门禁与 §6 的追踪规则承担 |
| 进度安排与人员资源（STP §5.2 / 5.3） | 没有可记录的排期与角色分工 |

被保留并改写成软件语境的是：范围与分工、质量目标、测试级别与类型、测试环境、测试项清单（指向用例集）、准入与准出、需求可追踪性、测试记录（指向执行记录）、缺陷分级、风险与质量保证。

写这一节的目的，是让刻意的裁剪不被误认为缺失的章节。
