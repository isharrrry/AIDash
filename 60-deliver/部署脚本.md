# AIDash 部署脚本说明

> 适用：Windows 10/11 + PowerShell 5.1+，AIDash 单进程、本机部署。
> 交付物：`60-deliver/scripts/deploy.ps1` + `60-deliver/scripts/backup-db.mjs`。
> 本文所有“代码依据”都标了文件与行号，便于复核；没核实的地方会明确写「未核实」。

## 1. 它解决什么问题

`start-aidash.ps1` 只负责“把服务启动起来”，而且以前台方式运行：不能停服务、不能备份、不能回滚。部署需要的是另一条流水线：

```
预检 -> 停服务 -> 备份数据库 -> 快照上一版构建 -> 构建 -> 启动 -> 健康检查
```

三条硬要求：

1. **幂等**：重复执行不产生第二个实例、不覆盖旧备份、不损坏数据库；
2. **失败即停**：任何一步失败，后续步骤不执行，并把“当前服务是什么状态、下一步去哪查”打印出来；
3. **可回滚**：部署前同时留下数据库备份和上一版构建快照，回滚方案才有东西可用。

`deploy.ps1` **不调用、不修改** `start-aidash.ps1`。后者必须保持 UTF-8 with BOM，且可能被其它流程引用。

## 2. 前置条件

| 条件 | 判据 / 说明 |
|---|---|
| Node.js ≥ 24 | `package.json:8` 的 `engines.node` 要求 `>=24.0.0`；脚本会解析 `node --version`，低于 24 直接失败 |
| pnpm 12.x | `package.json:10` 的 `packageManager` 是 `pnpm@12.4.1`；脚本只检查命令存在，不自动安装 |
| 依赖已安装 | `40-build/node_modules` 必须存在；缺了会提示执行 `pnpm -C 40-build install --frozen-lockfile`，脚本刻意不联网安装 |
| `AIDASH_TOKEN` 已设置 | 缺失时服务会 fail-fast（`config.ts:147-150`）；脚本在停服务**之前**就检查，避免停了才发现起不来 |
| 没有第二个部署在跑 | 脚本用 `data/deploy.lock` 做单实例锁；残留锁（PID 已不在）会自动清理 |
| 磁盘空间 | 至少能放下“当前库大小 × 保留份数 + 一份 dist 快照”；备份失败会停在第 2 步 |
| 端口占用者确认 | 只允许停“命令行同时包含 `dist/server/main.js` 与本仓库 `$RepoRoot`”的 node 进程（两边统一斜杠并转小写）；任一条件不满足都中止，不杀进程 |

> 注意：AIDash **不会自动读取 `.env` 文件**。`config.ts:138-150` 读的是 `process.env`；仓库里也没有 dotenv 依赖。所以 `.env` 只能当“清单”用，真正的值必须通过系统环境变量或启动脚本注入。

## 3. 用法

```powershell
# 只预检并打印计划：不停服务、不备份、不构建，**零副作用**
# （DryRun 判断在所有写操作之前：不建目录、不写锁、不清/采指标基线，也不发任何请求）
powershell -NoProfile -File .\60-deliver\scripts\deploy.ps1 -DryRun

# 正式部署（AIDASH_TOKEN 必须已经在当前进程的环境里）
powershell -NoProfile -File .\60-deliver\scripts\deploy.ps1
```

常用参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `-DryRun` | 关 | 只做预检和打印，不停服务、不备份、不构建；**零副作用**（不建目录、不写锁、不采指标基线、不发请求；DryRun 判断已在所有写操作之前） |
| `-Port` | 0 | 0 表示依次取 `AIDASH_PORT`、再退回 8787 |
| `-RepoRoot` | 自动推断 | 默认从脚本位置 `60-deliver/scripts` 往上两级 |
| `-KeepBackups` | 7 | 只清理本脚本生成的 `aidash-deploy-*.db`、`metrics-before-*.json` 与 `releases/` 快照，绝不碰 `pre-migrate-*` 或人工备份 |
| `-HealthTimeoutSeconds` | 30 | 启动后探活上限；NF-008 要求重启 ≤10s，30s 留了余量 |
| `-SkipBuild` | 关 | 跳过构建，直接用现有 dist；回滚“只换代码/只换库”时用 |

**执行策略**：脚本里没有、也不要使用 `-ExecutionPolicy Bypass`。如果系统策略阻止运行，按组织策略由管理员或当前用户设置（例如 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`），不要用 Bypass 绕过。

## 4. 每一步做什么、为什么、失败会怎样

### 0/6 预检

做这些事：

- 解析仓库根、数据库、备份、静态目录、日志目录、pid/锁文件的绝对路径；
- 检查 `node`、`pnpm`、`taskkill` 命令存在；
- 检查 Node 主版本 ≥24；
- 检查 `40-build/node_modules` 存在；
- 检查 `AIDASH_TOKEN` 非空（只检查存在，**不打印值**）；
- 检查端口当前占用者里没有非 node 进程（完整的“本仓库 + 入口”身份校验在停服步骤执行）；
- **库缺失但备份目录里有 `.db` 时直接失败**（`AIDASH_ALLOW_EMPTY_DB=true` 才放行）：主程序启动时也会拒绝这种状态，但那时服务已经停了；预检把这一步提到停服之前，避免为一个可预见的失败制造停机；
- 如果服务正在跑，**先确认监听者确实是本仓库的 AIDash（node 且命令行同时含 `dist/server/main.js` 与本仓库根）**，确认后才发一次带令牌的 `/api/metrics` 请求，把基线存到 `backups/metrics-before-<时间戳>.json`；确认不了就跳过、**不发令牌**；
- 以上全是只读检查；`-DryRun` 在这里打印计划就退出（零副作用）；
- 非 DryRun 才创建目录、获取单实例部署锁。

**失败时**：什么都还没改，服务保持原样。

为什么先确认身份再发令牌：端口可能被别的程序占着，`Authorization` 一发出去就泄露给了一个未知进程。基线只是“顺手做的对照”，不值得用令牌去换。判定与请求之间仍有极小的 TOCTOU 窗口（判断完端口可能换人），请求只发往回环地址；要彻底消除得按 socket 反查对端 PID，PowerShell 做不到。

### 1/6 停服务

- 先看 `data/aidash.pid`，再查端口监听者，两路 PID 去重；
- 每个 PID 都要过“身份校验”：必须是 `node`，且**归一化后的命令行同时包含 `dist/server/main.js` 和本仓库 `$RepoRoot`**；否则失败，**不杀**；
- 特别地：命令行含 `dist/server/main.js` 但不含本仓库根时归为 `unknown`，打印“疑似不是本仓库进程，请手工确认”并中止部署，**不执行 taskkill**；取不到命令行同样按 `unknown` 中止；
- 校验和停止分两阶段：先验完全部候选 PID，再统一 `taskkill`。任何一个身份不明都会在任何进程被停之前退出，避免“先停掉合法的、再被他仓库进程挡住”的半停机状态；
- 用 `taskkill /PID <pid> /T /F` 停进程；
- 等最多 15 秒确认端口释放；仍被占用就失败。

为什么是强杀而不是“优雅退出”：Windows 没有 POSIX 信号，Node 在 `main.ts:337-341` 注册的 `SIGTERM` 处理器在 Windows 上不会被 `taskkill`/`Stop-Process` 触发。与其假装优雅，不如明确强杀。数据安全性由 SQLite WAL 保证：已提交事务不会因为进程被杀而丢；下一步用 Backup API 备份时会把 `-wal` 中已提交但未 checkpoint 的页一并纳入。

`/T` 的作用是连同子进程一起停，避免留下孤儿进程占端口（见 `70-operate/已知坑清单.md:33`）。

**失败时**：服务可能仍在运行或端口仍被占；脚本不会继续备份/构建。身份不确定时脚本不会“先杀了再说”，而是把 PID、命令行和 `$RepoRoot` 打出来，等人确认。

### 2/6 备份数据库

- 库不存在或大小为 0：按首次部署跳过（启动时 `openDb` 会建库，`connection.ts:19-29`）；
- 否则调用 `backup-db.mjs`：
  1. `PRAGMA wal_checkpoint(TRUNCATE)`；`busy=1` 说明还有连接占用，直接失败；
  2. 用 better-sqlite3 的 `db.backup()`（SQLite 在线备份 API）生成 `<备份>.db`；
  3. 重新打开备份做 `PRAGMA integrity_check`，必须是 `ok`；
  4. 计算 sha256，写 `<备份>.sha256`；
- 脚本再用 PowerShell 独立算一次 sha256 对账，防止“写完了但内容不完整”；
- 按 `-KeepBackups` 清理本脚本自己的旧备份。

为什么不用 `Copy-Item`：WAL 模式下直接拷 `.db` 可能漏掉尚未 checkpoint 的页，得到“看起来成功、实际少了最近写入”的备份。设计 `30-design/设计文档包/05-数据库设计说明.md:859-876` 明确要求用 Backup API。

**失败时**：数据库没有被修改，但服务处于停止状态。不要绕过这一步继续启动；按 `报错预案.md` 的「备份失败」处理。

### 3/6 快照上一版构建

- 如果 `dist/server` 或 `dist/web` 存在，把 `server`、`shared`、`web` 三个子目录复制到 `backups/releases/<时间戳>/`；
- 写一个 `RELEASE.txt` 记录创建时间与用途；
- 按 `-KeepBackups` 清理旧快照。

为什么需要：构建失败时服务已经停了，旧 dist 又可能被 tsc/Vite 覆盖了一半。没有快照，回滚方案里的“只回滚代码”就无法执行。

`-SkipBuild` 时跳过本步：当前 dist 就是要启动的版本，不需要再快照。

### 4/6 构建

依次执行：

```powershell
pnpm -C 40-build build       # tsc 编译服务端 + 复制迁移 SQL
pnpm -C 40-build web:build   # Vite 构建前端
```

这两条来自 `40-build/package.json:15` 与 `:18`。`build` 只编译服务端并搬运 `.sql`，**不包含前端**；`web:build` 是独立脚本。只跑 `build` 会得到没有 `dist/web/index.html` 的部署。

构建后检查三个关键产物：

- `dist/server/main.js`
- `dist/server/db/migrations/000_bootstrap.sql`（`copy-server-assets.mjs` 的锚点）
- `dist/web/index.html`

**失败时**：服务保持停止。脚本会提示“上一版构建已快照在 `<路径>`”，修复后重跑，或按 `回滚方案.md` 恢复旧版本。这是“失败即停”的代价，必须如实告知，不能假装部署脚本能自动回退。

### 5/6 启动

- 把 `AIDASH_DB_PATH`、`AIDASH_BACKUP_DIR`、`AIDASH_STATIC_DIR`、`AIDASH_PORT` 钉死成绝对路径；
- 不强行覆盖 `AIDASH_HOST`：默认 127.0.0.1，用户显式设置时按用户的来；
- 把旧的 `server.out.log` / `server.err.log` 轮转到 `data/logs/server-<时间戳>.out.log`，避免 `Start-Process` 的重定向把上一次现场直接清空；
- `Start-Process node dist/server/main.js` 后台启动，stdout/stderr 落到 `data/server.out.log` / `data/server.err.log`；
- 进程一启动就登记到脚本级变量（在写 pid 文件之前），任何后续失败都能把它停掉；
- PID 写入 `data/aidash.pid`。

为什么钉死路径：`start-aidash.ps1:16-33` 已经踩过这个坑——相对路径会随启动目录漂移，指向另一个空库，表现出来就是“任务全没了”。`/healthz` 会返回解析后的 `db_path`（`app.ts:49-58`），部署脚本会拿它和预期路径逐字比对。

### 6/6 健康检查

两层：

1. **`/healthz`**（免鉴权、不计限流，`app.ts:49-58`）：必须返回 HTTP 200、`ok=true`、`status=ok`，且 `db_path` 与部署目标一致。路径不一致会立刻失败——这是最危险的启动异常：服务活着，但可能在读写另一个库。
2. **`/api/health`**（Bearer 鉴权，`admin.ts:180-192`）：必须返回 `ok=true`、`data.status=ok`、`data.audit_chain.ok=true`。这一层同时验证令牌、审计链和数据库可查询。

最后打印启动日志里的 `db_ready` / `listening` / `pre_migration_backup` 关键行，让人一眼确认“连的是哪个库、迁移做了什么”。

**失败时**：打印 stderr/stdout 最后 30 行；进程若已退出，打印退出码。**只要失败发生在启动之后，脚本会先 `taskkill /PID <pid> /T /F` 停掉本次启动的进程（含子进程），再清理 pid 文件与部署锁，然后才退出** —— 不留下「部署报失败、服务还在跑」的半截状态。

## 5. 幂等性怎么保证

| 重复执行场景 | 行为 |
|---|---|
| 服务本来就没起 | 停止步骤打印“跳过”，继续 |
| 连续部署两次 | 第二次先停掉第一次起的服务，再生成一份新备份、新快照，不会出现两个实例 |
| 同一秒内重复执行 | 备份文件名带毫秒；若仍撞名会拒绝覆盖并失败，不会写坏旧文件 |
| 备份目录里已有旧备份 | 只按保留策略删 `aidash-deploy-*`；`pre-migrate-*` 与人工备份不动 |
| 构建失败后重跑 | 重新构建；旧快照仍在，可先回滚 |
| 回滚后重跑 | 正常走完整流程，相当于一次新的部署 |

数据安全的关键顺序是“**先停服，再备份**”。只要服务还活着，备份就可能和写入并发；脚本不会在服务运行时做备份。

## 6. 边界：它不做什么

- **不安装依赖**：`node_modules` 缺失直接失败，避免部署时联网拉到不可控版本；
- **不跑测试**：测试应在部署前的 CI/本地门禁执行（`pnpm -C 40-build check`），生产部署脚本不承担测试职责；
- **不备份 `~/.aidash`**：数据库备份不包含页面保存 LLM 密钥的 `master.key` / `secrets.json`。主密钥丢失后旧密文永久解不开（`70-operate/已知坑清单.md:22`），需要单独备份，且不要和数据库备份放在同一个地方；
- **不轮换令牌**：令牌只从环境变量读，脚本只检查存在性；
- **不做 git 操作**：不 commit、不 checkout、不 tag；
- **不修改 `start-aidash.ps1`**；
- **不处理跨主机部署**：默认只监听回环地址。改成 `0.0.0.0` 属于部署方的显式选择，需要自行承担 TLS/反代与暴露面风险（`30-design/技术规格清单.md:51`）。

### 6.1 进程身份判断的已知限制

- **必须能读到命令行**：身份依赖 `Win32_Process.CommandLine`。权限不足、系统策略或 CIM 故障导致取不到命令行时，一律按 `unknown` 中止，不杀进程。
- **必须是绝对路径且真实指向本仓库**：命令行里要出现本仓库根的绝对路径（以及 `dist/server/main.js`）。用相对路径启动、通过 junction/符号链接别名启动、或把 `dist` 拷到仓库外运行，都会被判为 `unknown`，需要人工确认。
- **同前缀目录不误认**：比较时要求仓库根后面带 `/`，因此 `AIDash-old`、`AIDash2` 不会被当成 `AIDash`。但同一路径下的“替换进程”仍可能通过命令行伪装，这不是恶意进程防护；它的目标是避免部署脚本误杀别的 Node/AIDash。
- **TOCTOU 窗口仍在**：身份判断与实际 `taskkill` 之间进程可能变化。脚本在停服前重新判定一次，但没有按 socket 句柄锁定 PID；极小窗口内换人仍可能发生。

## 7. 和 ADR-016 的关系

ADR-016（`30-design/概要设计.md` §3；草案与实测证据见 `30-design/技术验证意见.md` 附录 A）的结论是**放弃 Node SEA 单文件打包，改为目录分发**，原因是 ESM/CJS 与 `better-sqlite3` 原生模块三条硬限制。该 ADR 已于 2026-10-25 **裁决为接受**。

本文与脚本按**目录分发**写：部署目标是一个包含 `40-build/`、Node 运行时与依赖的目录，不是单个 exe。若将来上游推翻该裁决，`deploy.ps1` 的“快照/启动/健康检查”结构仍然可用，只需要替换构建产物形态。
