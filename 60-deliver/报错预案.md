# AIDash 报错预案

> 适用：Windows 本机部署，使用 `60-deliver/scripts/deploy.ps1` 与 `start-aidash.ps1`。
> 每条按「**现象 → 判据 → 处置 → 升级条件**」写。判据不满足时不要硬套本条，先看下一条。
> 原则：**没有证据不下单一根因结论；涉及数据恢复必须先校验备份，再动手。**

## 0. 先看哪里

| 位置 | 看什么 |
|---|---|
| `40-build/10-aidash/data/server.out.log` | 结构化 JSON：`db_ready`、`listening`、`pre_migration_backup`、`http_request` |
| `40-build/10-aidash/data/server.err.log` | `startup_failed`、`pre_migration_backup_failed`、`db_missing_with_backups`、未捕获异常栈 |
| `40-build/10-aidash/data/logs/server-*.log` | 被 `deploy.ps1` 轮转的历史日志 |
| `GET /healthz` | **只证明进程活着、路由通**；免鉴权、不碰数据库；返回 `db_path` |
| `GET /api/health` | 需要 Bearer；返回 `status`、`audit_chain`、`waiting_requests` |
| `GET /api/metrics` | 卡片/任务按状态计数，用于对比部署前基线 |
| `data/aidash.pid` / `data/deploy.lock` | 当前服务 PID / 部署单实例锁 |

常用取证命令：

```powershell
Get-Content 40-build\10-aidash\data\server.err.log -Tail 50
Get-Content 40-build\10-aidash\data\server.out.log -Tail 50
Get-NetTCPConnection -LocalPort 8787 -State Listen -ErrorAction SilentlyContinue |
  Select-Object LocalAddress, LocalPort, OwningProcess
Get-Process -Id <PID> | Select-Object Id, ProcessName, Path
```

**升级分级**（全文统一）：

- **L1 自愈**：操作者按步骤能修，不涉及数据取舍；
- **L2 需用户确认**：会丢数据、要换库、要轮换令牌、要空库启动；
- **L3 停服 + 保留现场 + 升级**：原因不明、数据完整性可疑、回滚失败。

## 1. 端口被占

### 现象

- `deploy.ps1` 在停止或启动阶段失败；
- `server.err.log` 里出现 `EADDRINUSE` 或 `listen EADDRINUSE` 栈（具体输出形态**未实测**）；
- 启动后 `/healthz` 一直无响应，进程可能已经退出；
- `Get-NetTCPConnection -LocalPort 8787 -State Listen` 能看到别的 PID。

### 判据（满足任意一条）

1. 端口处于 `LISTENING`，且 owning PID 不是本次启动的 AIDash；
2. `server.err.log` 出现 `EADDRINUSE`；
3. 端口占用者不是 `node`，或命令行不同时包含 `dist/server/main.js` 与本仓库根的绝对路径。

### 处置

1. 查占用者：
   ```powershell
   Get-NetTCPConnection -LocalPort 8787 -State Listen |
     Select-Object LocalAddress, LocalPort, OwningProcess
   Get-CimInstance Win32_Process -Filter "ProcessId = <PID>" |
     Select-Object ProcessId, Name, CommandLine
   ```
2. **是本仓库 AIDash 的 node 进程**（命令行同时含 `dist/server/main.js` 与本仓库根）：用 `taskkill /PID <PID> /T /F` 停掉，再重跑 `deploy.ps1`。`/T` 是为了带走子进程，避免孤儿进程继续占端口（`70-operate/已知坑清单.md:33`）。命令行含 `dist/server/main.js` 但不在本仓库根下时，`deploy.ps1` 会判为 `unknown` 并中止、不杀进程；这种情况按下面第 3 条人工确认。
3. **不是 AIDash 的 node 进程**：不要杀。确认它是谁；能停就停，不能停就换端口：
   ```powershell
   powershell -NoProfile -File .\60-deliver\scripts\deploy.ps1 -Port <新端口>
   ```
   换端口后，所有 harness/值守壳的 `aidash_url` 都要同步改。
4. **是系统进程/服务**（如 `System`、`svchost`）：不要动，直接换端口或升级。
5. 如果只是 `TIME_WAIT`（状态不是 `LISTENING`）：通常不影响重新监听，等几十秒再试，不要杀进程。

### 升级条件

- **if** 占用者是系统服务或无法识别的进程 **then** 升级（L2/L3）；
- **if** 连续 2 次停止后端口仍被同一 PID 占用 **then** 升级；
- **if** 换端口会导致多个 harness 需要改配置，且用户不在场 **then** 暂停，先确认。

## 2. 数据库被锁（SQLITE_BUSY）

### 现象

- API 返回 500，日志里出现 `SQLITE_BUSY` 或 `database is locked`；
- `deploy.ps1` 在第 2 步失败，`backup-db.mjs` 报 `WAL checkpoint 失败：仍有连接占用数据库（busy=1）`；
- **`/healthz` 仍然返回 200**——它不碰数据库，不能用来判断锁。

### 判据（满足任意一条）

1. 错误文本包含 `SQLITE_BUSY` / `database is locked`；
2. 备份助手的 checkpoint 返回 `busy=1`；
3. 同一个 `aidash.db` 被两个 AIDash 进程或外部工具（DB 浏览器、备份软件、同步盘、杀毒扫描）同时打开。

### 处置

1. 确认只有一个 AIDash 实例：
   ```powershell
   Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" |
     Select-Object ProcessId, CommandLine
   ```
   命令行同时含本仓库根和 `dist/server/main.js` 的应该只有一个。多出来的先核对它属于哪个仓库/实例，再决定是否 `taskkill /PID <PID> /T /F` 停掉；不要仅凭 `dist/server/main.js` 就杀进程。
2. 停掉可能占用数据库的外部程序：DB 浏览器、同步盘、备份任务、杀毒扫描。
3. 看 WAL 大小：
   ```powershell
   Get-ChildItem 40-build\10-aidash\data\aidash.db* | Select-Object Name, Length, LastWriteTime
   ```
   `-wal` 持续增长说明有长事务或写入没停；先停服，再让 `backup-db.mjs` 做 checkpoint。
4. **服务运行时绝对不要删除 `-wal` / `-shm`**：那可能丢掉已提交事务。要清理只能停服后由 SQLite 自己做 checkpoint。
5. 处理完后重跑 `deploy.ps1`（它会先停、再备份、再启动）。

为什么 `busy_timeout` 是 5 秒：`connection.ts:26` 设了 `busy_timeout=5000`，短冲突会排队；超过 5 秒还拿不到锁才会报 `SQLITE_BUSY`。所以一旦看到这个错，通常不是“一瞬间的抖动”。

### 升级条件

- **if** 停掉所有其他进程后锁仍持续 >10 分钟 **then** 升级（L3）；
- **if** `integrity_check` 不是 `ok` **then** 升级，按 `回滚方案.md` 处理（L2）；
- **if** WAL 无限增长或磁盘被写满 **then** 停服并升级；
- **if** 怀疑是 AIDash 自身长事务 bug **then** 保留日志与 `request_id`，升级给开发。

## 3. 令牌缺失 / 令牌错误

### 现象

- 服务启动即退出，`server.err.log` 出现 `startup_failed`，错误码 `CONFIG_MISSING`，`keys: ["AIDASH_TOKEN"]`；
- 或服务正常启动，但 `/api/*`、`/mcp` 返回 401：`AUTH_REQUIRED` 或 `AUTH_INVALID_TOKEN`；
- 页面能打开（静态资源免鉴权），但一调 API 就 401。

### 判据

1. 启动失败 + `CONFIG_MISSING`：环境变量/配置文件里没有令牌；
2. `/healthz` 返回 200，但带当前环境令牌请求 `/api/health` 返回 401：进程里的令牌与调用方不一致；
3. 多个 harness 同时报 401，且它们用的是同一个旧令牌：疑似令牌被轮换或环境不一致。

### 处置

1. **只检查存在性，不打印值**：
   ```powershell
   if ([string]::IsNullOrWhiteSpace($env:AIDASH_TOKEN)) { '未设置' } else { '已设置' }
   ```
2. 未设置：通过系统“环境变量”或启动器设置 `AIDASH_TOKEN`，**重开终端**（环境变量不会自动同步到已开的窗口），再重跑部署。
3. 已设置但 401：
   - 确认服务进程是**在哪套环境**里启动的。`deploy.ps1` 继承当前 shell 的环境；如果你在 A 窗口设置、在 B 窗口部署，B 窗口可能没有。
   - 不要打印令牌；用同一份来源（密码管理器/用户环境变量）重新填到页面或 harness。
   - **改环境变量后必须重启服务**，运行中的进程不会重新读。
4. **401 不要重试**：重试只会把错误令牌刷进日志（`70-operate/已知坑清单.md:32`）。修好令牌再调用。
5. 疑似泄露：立即轮换令牌，并逐个更新 harness；轮换会让旧 harness 立刻 401（`30-design/设计文档包/06-安全性设计支撑材料.md:114-117`、`:217`）。轮换顺序必须是“先验证新令牌可用，再失效旧令牌”，反了会把所有 harness 锁在门外。

### 升级条件

- **if** 确认环境变量一致但 `/api/health` 仍 401 **then** 升级（L3），保留 `x-request-id` 与时间点；
- **if** 怀疑令牌泄露 **then** 立即 L2：轮换 + 全量通知，不要等；
- **if** 轮换后多个 harness 无法同步更新 **then** 升级，安排停机窗口。

## 4. 构建失败

### 现象

- `deploy.ps1` 在第 4 步退出，服务保持停止；
- `pnpm -C 40-build build` 或 `web:build` 返回非 0；
- 或构建命令成功，但产物检查失败：缺 `dist/server/main.js`、`dist/server/db/migrations/000_bootstrap.sql`、`dist/web/index.html`。

### 判据

1. 构建命令退出码非 0；
2. `copy-server-assets.mjs` 报 `migrations source missing` 或 `copy verification failed`；
3. 产物缺失（`deploy.ps1` 会逐个检查）；
4. 运行时日志出现 `MIGRATIONS_DIR_NOT_FOUND`（说明迁移 SQL 没进 dist）。

### 处置

1. 先看具体错误：
   ```powershell
   pnpm -C 40-build typecheck
   ```
   这会同时检查服务端与前端 TypeScript（`package.json:16`），比只跑 `build` 更容易定位。
2. 依赖缺失：`40-build/node_modules` 不存在时，执行
   ```powershell
   pnpm -C 40-build install --frozen-lockfile
   ```
   网络慢时用你所在环境配置的国内镜像；**不要改 `pnpm-lock.yaml` 来“绕过”问题**。
3. `better-sqlite3` 原生模块问题：确认 Node 主版本 ≥24；必要时重建：
   ```powershell
   pnpm -C 40-build rebuild better-sqlite3
   ```
4. 修复后重跑 `deploy.ps1`（幂等）。
5. **紧急恢复**：如果短时间修不好，按 `回滚方案.md` §4 用 `backups/releases/<时间戳>/` 恢复上一版 `dist`，再执行：
   ```powershell
   powershell -NoProfile -File .\60-deliver\scripts\deploy.ps1 -SkipBuild -KeepBackups 30
   ```

### 升级条件

- **if** 修复后连续 2 次构建仍失败 **then** 升级（L2）；
- **if** 失败原因是依赖/lockfile 冲突或 TypeScript 主版本升级 **then** 升级给开发，不要在生产机上大改依赖；
- **if** 原生模块在当前机器缺编译工具链 **then** 升级，评估换机器或预编译产物。

## 5. 迁移失败

### 现象

- 服务启动后很快退出；`server.err.log` 有 `startup_failed`；
- 错误码是 `MIGRATION_FAILED`、`MIGRATION_CHECKSUM_MISMATCH` 或 `MIGRATIONS_DIR_NOT_FOUND`；
- 没有出现 `db_ready`；端口没有监听；
- `backups/` 里可能出现 `pre-migrate-<from>-to-<to>-<时间戳>.db`。

### 判据

1. `MIGRATION_FAILED`：某个新迁移的 SQL 执行失败；该文件在事务内回滚（`migrate.ts:94-109`）；
2. `MIGRATION_CHECKSUM_MISMATCH`：已经应用过的迁移文件被改过，和 `schema_migration` 里记录的 checksum 不一致（`migrate.ts:81-89`）；
3. `MIGRATIONS_DIR_NOT_FOUND`：`dist` 里没有迁移目录或 `000_bootstrap.sql`。

### 处置

1. **不要修改已经应用过的迁移文件**。checksum 已经记录在库里；改一个字符就会让服务拒绝启动。要改只能新增一个迁移。
2. **新迁移写错**：修这个还没成功应用的迁移文件，重跑部署。单文件事务会把失败的改动回滚，`schema_version` 应该还停在上一个版本。
3. **checksum 不匹配**：把原迁移文件恢复成历史版本（从版本库/发布包取回），不要手工改 `schema_migration.checksum`——那等于伪造迁移历史。
4. **库状态不明**：停服，按 `回滚方案.md` §5 恢复 `pre-migrate-*` 或本次部署前备份；**恢复时连 `-wal` / `-shm` 一起改名**。
5. **特别注意**：`main.ts:66-72` 里“迁移前备份失败”只记 `pre_migration_backup_failed` 警告，**不会阻止迁移**。如果日志里有这条，说明自动的迁移前备份可能不存在，只能用 `deploy.ps1` 生成的 `aidash-deploy-*.db`。所以部署前一定要确认第 2 步备份成功。
6. 排查时可以用离线只读查询看当前版本：
   ```powershell
   node -e "const {createRequire}=require('node:module');const D=createRequire(process.cwd()+'/40-build/package.json')('better-sqlite3');const db=new D(process.argv[1],{readonly:true,fileMustExist:true});console.log(db.prepare('SELECT version, description, applied_at FROM schema_migration ORDER BY version').all());db.close()" "40-build/10-aidash/data/aidash.db"
   ```

### 升级条件

- **if** 迁移失败影响到表结构或数据 **then** 立即停服并 L2；
- **if** 没有一份校验通过的可用备份 **then** L3，不要继续尝试“修一修再启动”；
- **if** 需要“向下迁移”（回退 schema）而迁移框架没有 down 脚本 **then** 升级，由人决定恢复策略；
- **if** 同一迁移连续 2 次失败且原因不明 **then** L3，保留日志与库文件。

## 6. 备份失败

### 现象

- `deploy.ps1` 在第 2 步退出，服务保持停止；
- 没有生成 `aidash-deploy-*.db`，或文件大小为 0；
- `.sha256` 缺失/不匹配；`integrity_check` 不是 `ok`；
- 备份助手退出码 1（2 表示源库不存在/为空，属于首次部署的跳过）。

### 判据（满足任意一条）

1. 助手输出 `FAIL:`；
2. `WAL checkpoint` 返回 `busy=1`；
3. 目标目录不可写、磁盘满、路径不存在；
4. 目标文件已存在（助手拒绝覆盖）；
5. 无法从 `40-build/node_modules` 加载 `better-sqlite3`；
6. `integrity_check != ok`。

### 处置

1. 查磁盘与权限：
   ```powershell
   Get-PSDrive -PSProvider FileSystem | Select-Object Name, Free, Used
   New-Item -ItemType File -Path '40-build\10-aidash\backups\.write-test' -Force |
     Remove-Item -Force
   ```
2. 确认服务已停止、没有第二个进程占用数据库（见第 2 条）。
3. 目标文件已存在：改名保留，不要覆盖；然后重跑。
4. `better-sqlite3` 加载失败：先在 `40-build` 下验证：
   ```powershell
   node -e "console.log(typeof require('better-sqlite3'))"
   ```
   失败就重新安装依赖（`pnpm -C 40-build install --frozen-lockfile`）。
5. **没有通过校验的备份，不要继续构建/启动**。如果业务紧急、用户明确接受“无备份部署”的风险，必须记录在案（谁批准、什么时间、风险是什么），并先手工把当前 `aidash.db` + `-wal` + `-shm` 复制到另一个磁盘——**这只是应急副本，不能替代 Backup API 的一致性快照**。
6. 备份不包含 `~/.aidash` 下的主密钥；主密钥要单独备份（`70-operate/已知坑清单.md:22`）。

### 升级条件

- **if** 磁盘满或文件系统报错 **then** 升级（L2），不要边清磁盘边部署；
- **if** 同一路径连续 2 次备份失败 **then** 升级；
- **if** 用户要求“无备份继续部署” **then** 必须 L2 明确确认，并记录风险；
- **if** 备份文件校验失败但原库看起来正常 **then** 先保原库，L3 查原因（可能是磁盘/驱动问题）。

## 7. 健康检查失败 / 启动即退出

### 现象

- `deploy.ps1` 第 6 步失败：30 秒内 `/healthz` 没成功；
- 或进程启动后立刻退出，退出码非 0；
- 或 `/healthz` 通过，但 `/api/health` 失败。

### 判据

1. 进程 `HasExited=true`；
2. `/healthz` 连续超时/连接拒绝；
3. `/healthz` 返回的 `db_path` 与部署目标不一致；
4. `/api/health` 返回 401、非 ok、或 `audit_chain.ok=false`。

### 处置

1. 看日志尾部（`deploy.ps1` 已自动打印 30 行）：
   - `CONFIG_MISSING` → 第 3 条；
   - `EADDRINUSE` → 第 1 条；
   - `DB_MISSING_WITH_BACKUPS` → 第 8 条；
   - `MIGRATION_*` → 第 5 条；
   - 其他未捕获栈 → 保留完整 stderr，L3。
2. `db_path` 不一致：**立即停掉这个服务**，确认 `AIDASH_DB_PATH` 与启动目录；不要让它继续读写错误库。
3. `/api/health` 401：第 3 条；`audit_chain.ok=false`：停止写入，按 `回滚方案.md` R9 处理。
4. 进程活着但 `/healthz` 不通：确认监听地址与探针地址一致（`AIDASH_HOST=0.0.0.0` 时探针应打回环地址），并检查防火墙/安全软件。

### 升级条件

- **if** 连续 2 次启动失败且日志没有明确错误码 **then** L3；
- **if** `db_path` 指向了非预期文件 **then** 立即 L3，先确认数据在哪；
- **if** 审计链断裂 **then** L3，不要自动回滚掩盖证据。

## 8. 空库误连守卫（`DB_MISSING_WITH_BACKUPS`）

### 现象

- 服务启动失败，`server.err.log` 出现 `db_missing_with_backups`；
- 错误详情里有 `db_path`、`backup_dir`、`backup_count`、`latest_backup`；
- 页面打不开，或刚打开就发现“任务全没了”。

### 判据

配置的 `AIDASH_DB_PATH` 指向的文件不存在，但备份目录里存在 `*.db`，且 `AIDASH_ALLOW_EMPTY_DB` 不是 `true`（`main.ts:256-284`、`startup.ts:49-74`）。

### 处置

1. **先当作路径漂移处理**，不要急着建空库：
   - 检查 `AIDASH_DB_PATH` 是不是绝对路径；
   - 检查启动目录是不是仓库根；
   - 在磁盘上找 `aidash.db` 的真实位置。
2. 找到正确库：把路径改回去，重跑部署。
3. 确认是全新安装、备份目录里的文件与本机无关：才临时设 `AIDASH_ALLOW_EMPTY_DB=true` 建空库；建完后**立刻去掉这个变量**，不要长期保留。
4. 如果确实找不到原库：按 `回滚方案.md` §5 用最近一份通过校验的备份恢复。

### 升级条件

- **if** 找不到原库但备份存在 **then** L2：由用户确认恢复到哪个时间点；
- **if** 备份也找不到/校验失败 **then** L3，按 `回滚方案.md` §8 兜底；
- **if** 有人为了“先跑起来”想直接建空库 **then** 必须 L2 明确告知“数据看起来会全没”，并保留现场。

## 10. 升级时怎么给证据

升级（L2/L3）时至少给这些，**不要给令牌明文**：

1. 时间点（精确到分钟）与 `deploy.ps1` 的时间戳；
2. 失败步骤与退出码；
3. `server.err.log` 最后 30 行（如含令牌，先脱敏）；
4. `/healthz`、`/api/health` 的返回（`db_path`、`status`、`audit_chain`）；
5. 备份文件名、大小、sha256、`integrity_check` 结果；
6. 已经做过的处置与结果；
7. 当前服务状态：运行 / 停止 / 端口被谁占用。
