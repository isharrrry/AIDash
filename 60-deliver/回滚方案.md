# AIDash 回滚方案

> 适用版本：AIDash 2.0.0（单进程、SQLite、Windows 本机部署）。
> 配套脚本：`60-deliver/scripts/deploy.ps1`、`60-deliver/scripts/backup-db.mjs`、`60-deliver/scripts/restore-db.mjs`。
> 原则：**先保数据，再保服务；每一步都可验证；回滚本身也要留证据。**

## 0. 先把“回滚”拆成三种

| 类型 | 什么时候用 | 会丢什么 |
|---|---|---|
| **只回滚代码** | 新代码有 bug，但数据库 schema 没变、数据没坏 | 不丢数据；只回到上一版 `dist` |
| **只回滚数据** | 代码没问题，但库被写坏/迁移失败/连错库 | 会丢掉“备份时间点之后”的所有写入 |
| **全量回滚（代码 + 数据）** | 新版本同时改了代码和 schema，或原因不明 | 同“只回滚数据”，且代码回到上一版 |

**关键判断：本次部署有没有执行 schema 迁移？**
如果执行了，**不要只回滚代码**——旧代码可能不认识新表/新列。判断方法（三选一，都基于已有产物）：

```powershell
# 1) 启动日志里 db_ready 的 applied 数组非空
Select-String -Path 40-build\10-aidash\data\server.out.log -Pattern '"msg":"db_ready"'

# 2) 备份目录里出现本次启动生成的迁移前备份
Get-ChildItem 40-build\10-aidash\backups -Filter 'pre-migrate-*.db' |
  Sort-Object LastWriteTime -Descending | Select-Object -First 3 Name, LastWriteTime

# 3) 离线查 schema 版本（只读；需要 40-build/node_modules 里的 better-sqlite3）
node -e "const {createRequire}=require('node:module');const D=createRequire(process.cwd()+'/40-build/package.json')('better-sqlite3');const db=new D(process.argv[1],{readonly:true,fileMustExist:true});console.log(db.prepare('SELECT MAX(version) AS v FROM schema_migration').get());db.close()" "40-build/10-aidash/data/aidash.db"
```

> 注意：`/healthz` 与 `/api/health` **都没有返回 schema_version**（已核实 `app.ts:49-58`、`admin.ts:180-192`），和 REQ-FN-064 的验收描述不一致。所以只能靠上面的日志/备份名/离线查询判断。

## 1. 触发条件（必须能写成 if）

数据来源只有四类，别假设有 Prometheus：

- `data/server.out.log` / `data/server.err.log`（JSON 行，`log.ts:17-36`）；
- `data/logs/server-*.log`（历史轮转日志）；
- `/healthz`、`/api/health`、`/api/metrics`（`app.ts:49-58`、`admin.ts:180-210`）；
- 进程与端口状态、备份文件的 sha256 / `integrity_check`。

> **前提**：要算 5xx 率，`AIDASH_LOG_LEVEL` 必须是 `info`（默认值）。设成 `warn` 时 `http_request` 行不会写，5xx 率算不出来，只能靠探针。

### 1.1 回滚触发表

| 编号 | 条件（可直接写成 if） | 阈值 | 持续时间 | 数据来源 | 动作 |
|---|---|---|---|---|---|
| **R1** | `if deploy_healthcheck == fail then rollback` | `/healthz` 在 30 秒内没有一次成功 | 立即 | `deploy.ps1` 退出码 + `/healthz` | 全量回滚（先代码，再判断是否需要回数据） |
| **R2** | `if http_5xx_rate > 5% and http_requests_5min >= 20 then rollback` | 5%；样本 ≥20 请求 | 连续 10 分钟（两个 5 分钟窗口都超） | `server.out.log` 的 `http_request.status` | 只回滚代码 |
| **R3** | `if process_exit_count >= 3 then rollback` | 3 次 | 30 分钟内 | pid/端口探测 | 只回滚代码 |
| **R4** | `if healthz_consecutive_failures >= 3 then rollback` | 3 次，每次超时 5 秒 | 约 15 秒 | 外部探针 | 先查进程；排除环境问题后只回滚代码 |
| **R5** | `if db_integrity_check != 'ok' then rollback` | 任意非 `ok` | 立即 | `backup-db.mjs --verify` 或离线检查 | 只回滚数据（用最近一份通过校验的备份） |
| **R6** | `if card_count < pre_deploy_card_count * 0.90 or task_count < pre_deploy_task_count * 0.90 then rollback` | 低于基线 90%；基线 ≥10 | 持续 5 分钟 | `/api/metrics` + `backups/metrics-before-*.json` | 只回滚数据（先确认不是连错库） |
| **R7** | `if startup_error in ('MIGRATION_FAILED','MIGRATION_CHECKSUM_MISMATCH') then rollback` | 出现 1 次 | 立即 | `server.err.log` / `startup_failed` | 只回滚数据（回到 `pre-migrate-*` 或本次部署前备份） |
| **R8** | `if auth_401_rate > 50% and auth_requests_10min >= 10 then config_rollback` | 50%；样本 ≥10 | 连续 10 分钟 | 日志 401 + harness 报错 | **配置回退**，不是代码回滚 |
| **R9** | `if audit_chain.ok == false then stop_and_escalate` | 出现 1 次 | 立即 | `/api/health` 的 `data.audit_chain.ok` | 停止写入并升级，**不自动回滚** |

### 1.2 为什么是这些阈值

- **5% / 10 分钟**：单用户本机工具，偶发一个 500 不代表版本坏了；但 5 分钟内至少 20 个请求里超过 5% 是 5xx，且连续两个窗口都这样，说明是稳定故障，不是抖动。
- **90% / 5 分钟 / 基线 ≥10**：卡片/任务数量掉超过 10%，已经超出“筛选/归档造成的视觉差异”；很可能是连到了空库或错库。基线小于 10 时数字噪声太大，不触发。
- **3 次退出 / 30 分钟**：崩溃循环，重启也救不回来。
- **15 秒连续探活失败**：NF-008 要求重启 ≤10s（`20-spec/需求与验收判据文档.md:313`），15 秒没有任何响应已经不正常。
- **完整性/迁移错误立即回滚**：这两类问题继续跑只会扩大损坏面。

### 1.3 怎么算这些指标

**5xx 率（近 5 分钟）**：

```powershell
$dataDir = '40-build\10-aidash\data'
$files = @(Get-ChildItem $dataDir -Filter 'server*.log' -File -ErrorAction SilentlyContinue)
$files += @(Get-ChildItem (Join-Path $dataDir 'logs') -Filter 'server-*.log' -File -ErrorAction SilentlyContinue)
$since = (Get-Date).AddMinutes(-5)

$events = foreach ($f in $files) {
  Get-Content $f.FullName -ErrorAction SilentlyContinue | ForEach-Object {
    try { $_ | ConvertFrom-Json } catch { $null }
  }
}
$requests = @($events | Where-Object {
  $_ -and $_.msg -eq 'http_request' -and ([datetime]$_.ts) -ge $since
})
$total = $requests.Count
$bad = @($requests | Where-Object { [int]$_.status -ge 500 }).Count
$rate = if ($total -gt 0) { $bad / $total } else { 0 }
if ($total -ge 20 -and $rate -gt 0.05) {
  "R2 触发：总请求 $total，5xx $bad，比例 $([math]::Round($rate * 100, 2))%"
} else {
  "R2 未触发：总请求 $total，5xx $bad"
}
```

**卡片/任务总数（和部署前基线比）**：

```powershell
$headers = @{ Authorization = "Bearer $($env:AIDASH_TOKEN)" }
$m = Invoke-RestMethod 'http://127.0.0.1:8787/api/metrics' -Headers $headers
$cardsNow = ($m.data.cards_by_status.PSObject.Properties.Value | Measure-Object -Sum).Sum
$tasksNow = ($m.data.tasks_by_status.PSObject.Properties.Value | Measure-Object -Sum).Sum

$before = Get-Content -Raw '40-build\10-aidash\backups\metrics-before-<部署时间戳>.json' | ConvertFrom-Json
$cardsBefore = ($before.data.cards_by_status.PSObject.Properties.Value | Measure-Object -Sum).Sum
$tasksBefore = ($before.data.tasks_by_status.PSObject.Properties.Value | Measure-Object -Sum).Sum

if ($cardsBefore -ge 10 -and $cardsNow -lt ($cardsBefore * 0.9)) { 'R6 触发：卡片数骤降' }
if ($tasksBefore -ge 10 -and $tasksNow -lt ($tasksBefore * 0.9)) { 'R6 触发：任务数骤降' }
"卡片 before=$cardsBefore now=$cardsNow；任务 before=$tasksBefore now=$tasksNow"
```

> `metrics-before-*.json` 是 `deploy.ps1` 在停服前用 `/api/metrics` 采集的；服务当时没在跑或令牌不一致时不会生成，R6 就只能人工拿部署前的页面数字对比。

### 1.4 明确“不是回滚条件”的情况

| 现象 | 为什么不该自动回滚 | 正确动作 |
|---|---|---|
| `/api/health` 里 `audit_chain.ok=false` | 审计链断裂可能是人为改库/数据篡改，回滚会掩盖证据 | **停止写入、保留现场、升级给人**（R9） |
| 401 突然增多 | 令牌是环境变量，不在版本里；回滚代码不会换令牌 | **配置回退**：核对/恢复 `AIDASH_TOKEN`（R8） |
| 单个 500 或偶发超时 | 样本不足，回滚代价大于收益 | 记录 `request_id`，观察；达到 R2 再回滚 |
| 页面打不开但 `/healthz` 正常 | 可能只是前端静态资源/浏览器缓存 | 先查 `dist/web` 与浏览器控制台，不要直接回滚数据库 |

## 2. 回滚窗口

| 窗口 | 时长 | 依据与限制 |
|---|---|---|
| **代码回滚窗口** | `backups/releases/<时间戳>/` 还在就能回 | 默认保留最近 7 份；恢复时建议 `-KeepBackups 30`，避免回滚源被保留策略清掉 |
| **数据回滚窗口（推荐）** | 部署完成后 **30 分钟内** | 恢复的是“部署前备份”，部署后的新卡/新任务/新审计会丢；30 分钟是单用户本机工具的可接受损失判断，不是代码保证 |
| **数据回滚窗口（硬上限）** | 该备份未被保留策略清掉之前 | 默认最近 7 份 `aidash-deploy-*`；超过 7 次部署后，旧备份会被自动清理 |
| **RPO / RTO** | RPO ≤24h，RTO ≤1h | `05-数据库设计说明.md:899-901`、`20-spec/需求与验收判据文档.md:316`（NF-011） |

**超过 30 分钟还要回数据时**，必须先做两件事：

1. 明确告诉用户“会丢失哪些写入”，并得到确认；
2. 把“备份时间点之后创建的卡片/任务”尽量导出留档。当前列表接口没有 `created_after` 过滤（已核实 `http/routes/cards.ts:88-102`、`tasks.ts:65-73`），只能用页面按时间排序人工看，或停服后离线 SQL 查询。**离线查询属于未核实操作**，执行前先复制一份库。

## 3. 回滚前必做（三件事，顺序不能反）

1. **停服务**：回滚期间绝不能让进程继续写库。
2. **保留现场**：当前库、`-wal`、`-shm`、日志、`dist` 都不要删，改名保留。
3. **校验回滚源**：sha256 对得上、`integrity_check=ok`，否则换下一份备份。

```powershell
# 停服务（只停 node；非 node 占用先人工确认）
$port = if ($env:AIDASH_PORT) { [int]$env:AIDASH_PORT } else { 8787 }
$conns = @(Get-NetTCPConnection -LocalPort $port -State Listen -ErrorAction SilentlyContinue)
foreach ($c in $conns) {
  $p = Get-Process -Id $c.OwningProcess -ErrorAction SilentlyContinue
  if (-not $p) { continue }
  if ($p.ProcessName -ne 'node') { throw "端口 $port 被 $($p.ProcessName) 占用，先确认，不要盲杀" }
  & taskkill /PID $p.Id /T /F
}
Start-Sleep -Seconds 2
if (@(Get-NetTCPConnection -LocalPort $port -State Listen -ErrorAction SilentlyContinue).Count -gt 0) {
  throw "端口 $port 未释放，先处理占用再回滚"
}
Remove-Item '40-build\10-aidash\data\aidash.pid' -Force -ErrorAction SilentlyContinue
```

```powershell
# 校验备份（换成实际的备份文件名）
$bak = '40-build\10-aidash\backups\aidash-deploy-<时间戳>.db'
$want = ((Get-Content -Raw "$bak.sha256").Trim() -split '\s+')[0].ToLower()
$got = (Get-FileHash -Path $bak -Algorithm SHA256).Hash.ToLower()
if ($got -ne $want) { throw "sha256 不匹配，拒绝使用这份备份" }

# 只读校验：integrity_check 必须 ok，并打印 sha256 供二次核对
# 注意：这是一次只读「打开」，SQLite 会在备份旁边临时生成 -wal/-shm；
# 脚本只删本次新建的副文件，所以校验完目录应恢复原样。看到残留副文件说明清理失败，
# 它不影响这份备份的可信度，但别把它当成备份的一部分。
node .\60-deliver\scripts\backup-db.mjs --verify $bak
```

## 4. 步骤 A：只回滚代码

**前提**：本次部署没有执行 schema 迁移（见 §0）；如果有，跳到步骤 C。

```powershell
# 1) 找到失败那次部署留下的“上一版构建”快照（时间戳来自 deploy.ps1 输出）
$stamp = '<失败部署的 release 时间戳>'
$release = "40-build\10-aidash\backups\releases\$stamp"
foreach ($sub in @('server', 'shared', 'web')) {
  if (-not (Test-Path (Join-Path $release $sub))) { throw "快照缺少 $sub，不能只回滚代码" }
}

# 2) 保留坏掉的 dist（改名，不删）
$dist = '40-build\10-aidash\dist'
$badDist = "40-build\10-aidash\dist.bad-$(Get-Date -Format yyyyMMdd-HHmmss)"
if (Test-Path $dist) { Rename-Item -Path $dist -NewName (Split-Path $badDist -Leaf) }

# 3) 用快照恢复同名子目录
New-Item -ItemType Directory -Force -Path $dist | Out-Null
foreach ($sub in @('server', 'shared', 'web')) {
  Copy-Item -Path (Join-Path $release $sub) -Destination (Join-Path $dist $sub) -Recurse -Force
}
```

```powershell
# 4) 启动并做健康检查；-SkipBuild 表示不再重新编译，直接用刚恢复的 dist
powershell -NoProfile -File .\60-deliver\scripts\deploy.ps1 -SkipBuild -KeepBackups 30
```

> 用 `deploy.ps1` 启动而不是手工 `node`，是为了复用同一套 `/healthz` + `/api/health` 校验和日志打印。`-KeepBackups 30` 是为了在恢复期间不清理回滚源。

## 5. 步骤 B：只回滚数据

**前提**：代码是可信的，只是库需要回到某个时间点。

```powershell
# 0) 先按 §3 停服并校验备份（sha256 与 integrity_check 都要过）
$bak = '40-build\10-aidash\backups\aidash-deploy-<时间戳>.db'
$port = if ($env:AIDASH_PORT) { [int]$env:AIDASH_PORT } else { 8787 }

# 1) 交给恢复助手。它按固定顺序执行：
#    sha256 → integrity_check → 端口探活 → 现场快照 → 删旧 -wal/-shm → 原子替换 → 落地复验
node .\60-deliver\scripts\restore-db.mjs --db .\40-build\10-aidash\data\aidash.db --from $bak --port $port
```

恢复助手的几条硬约束（都是刻意的，不是可以顺手放宽的配置）：

- **缺 `<备份>.sha256` 时默认拒绝**：没有校验和就无法证明备份没被改坏。确认要跳过时加 `--allow-missing-sha256`，并在记录里写明原因。
- **端口有人监听就拒绝**：防止在服务运行时换库。§3 的停服步骤不能省。
- **覆盖前必须先留现场快照**：默认写到目标库同目录的 `pre-restore-<时间戳>.db`（可用 `--safety-dir` 指定），自带 `.sha256`。恢复错了要回退，就用它。
- **旧 `-wal` / `-shm` 会被删除**，而不是改名保留。删除发生在安全快照之后：快照要用到它们；之后若仍留在原地，SQLite 会把旧库的 WAL 页重放到新库上，比不回滚更糟。现场快照已经承担了“保留证据”的职责。
- 每次成功恢复都会在目标库目录追加一行 `restore.log`（来源、sha256、现场快照路径）。

```powershell
# 2) 启动 + 健康检查
powershell -NoProfile -File .\60-deliver\scripts\deploy.ps1 -SkipBuild -KeepBackups 30
```

> 回滚数据后，`deploy.ps1` 会先对“恢复后的库”再做一次备份，这是正常的：它记录的是回滚后的状态，不是回滚源。

<details>
<summary>手工兜底步骤（只在恢复助手本身跑不起来时使用）</summary>

手工路线的关键点与助手一致：先校验、先留旧库、连 `-wal` / `-shm` 一起处理。

```powershell
# 1) 先复制到临时文件，确认大小一致；避免“复制一半中断”直接把原库写坏
$data = '40-build\10-aidash\data'
$ts = Get-Date -Format 'yyyyMMdd-HHmmss'
$staging = Join-Path $data "aidash.db.restore-$ts"
Copy-Item -Path $bak -Destination $staging
if ((Get-Item $staging).Length -ne (Get-Item $bak).Length) { throw '恢复副本不完整，停止' }

# 2) 当前库与 WAL/SHM 一起改名保留（不要只换 .db）
$pairs = @(
  @{ From = 'aidash.db';     To = "aidash.db.bad-$ts" },
  @{ From = 'aidash.db-wal'; To = "aidash.db.bad-$ts-wal" },
  @{ From = 'aidash.db-shm'; To = "aidash.db.bad-$ts-shm" }
)
foreach ($pair in $pairs) {
  $src = Join-Path $data $pair.From
  if (Test-Path $src) { Move-Item -Path $src -Destination (Join-Path $data $pair.To) }
}

# 3) 把恢复副本就位
Move-Item -Path $staging -Destination (Join-Path $data 'aidash.db')
```

**为什么必须连 `-wal` / `-shm` 一起处理**：如果只替换 `.db` 而把旧 `-wal` 留在原地，SQLite 下次打开时可能把旧库的 WAL 页重放到新库上，结果比不回滚更糟。

</details>

> 恢复助手的行为可以用 `node 60-deliver/scripts/tests/restore-drill.mjs` 在本机演练一遍（临时库，不碰真实库）；最近一次记录在 [演练记录](./50-verify/演练记录/)。

## 6. 步骤 C：全量回滚

顺序：**先回数据，再回代码，最后启动**。

1. 按 §3 停服并校验备份；
2. 按 §5 换库（优先用恢复助手；旧 `-wal` / `-shm` 由其删除，手工路线才改名保留）；
3. 按 §4 恢复 `dist`（步骤 A 的 1~3）；
4. 执行 `deploy.ps1 -SkipBuild -KeepBackups 30`；
5. 按 §7 逐条验证。

为什么先数据后代码：如果先启动旧代码、再换库，中间会有一段“旧代码 + 新库”的窗口，可能触发不兼容写入；全部就位后再启动，窗口为零。

## 7. 回滚后验证清单

逐条打勾，任何一条不通过都不能宣布“回滚成功”：

- [ ] `/healthz` 返回 HTTP 200、`ok=true`、`status=ok`；
- [ ] `/healthz` 的 `db_path` 等于预期绝对路径（防止路径漂移）；
- [ ] `/api/health` 返回 `ok=true`、`data.status=ok`、`data.audit_chain.ok=true`；
- [ ] `/api/metrics` 的卡片/任务总数与“应该恢复到的备份时点”一致；与部署前基线对比，差异能解释；
- [ ] 恢复后的备份文件 sha256 校验通过；
- [ ] 恢复后的库 `integrity_check=ok`（`backup-db.mjs --verify` 对当前 `aidash.db` 再跑一次）；
- [ ] 页面能打开，`dist/web/index.html` 与静态资源 200；
- [ ] MCP 客户端能完成一次 `task.list`（不需要写操作）；
- [ ] 用一条**专用测试通道**发一张卡并回答，确认“发卡 → 回答 → 状态变化”链路正常；不要在真实业务通道造脏数据；
- [ ] 日志出现 `listening`、`db_ready`，没有新的 `startup_failed`；
- [ ] 观察 30 分钟：无崩溃、无 5xx 率回升、无端口异常；
- [ ] 按 `70-operate/故障记录模板.md` 记录回滚时间线，并写明“丢失了哪个时间点之后的写入”。

验证命令示例：

## 8. 回滚也失败时的兜底

回滚失败的定义：**执行完 §4/§5/§6 后，§7 仍有任意一条不通过。**

按下面顺序做，**每一步都不许删原件**：

1. **立即停止继续尝试**：不要反复启动/停止、不要反复覆盖库。每次失败尝试都在增加现场噪声。
2. **保留现场**：
   ```powershell
   $incident = Join-Path $env:TEMP "aidash-incident-$(Get-Date -Format yyyyMMdd-HHmmss)"
   New-Item -ItemType Directory -Force -Path $incident | Out-Null
   Copy-Item '40-build\10-aidash\data\aidash.db*' $incident -Force -ErrorAction SilentlyContinue
   Copy-Item '40-build\10-aidash\data\server*.log' $incident -Force -ErrorAction SilentlyContinue
   Copy-Item '40-build\10-aidash\data\logs' $incident -Recurse -Force -ErrorAction SilentlyContinue
   Get-ChildItem '40-build\10-aidash\backups' -File |
     Select-Object Name, Length, LastWriteTime |
     Export-Csv (Join-Path $incident 'backups.csv') -NoTypeInformation -Encoding UTF8
   ```
3. **换一份备份再试**：按时间从新到旧，列出所有 `aidash-deploy-*.db`，对每一份先 `sha256` + `--verify`；只用“两项都通过”的最接近目标时点的备份。不要在同一份坏备份上反复恢复。
4. **换一份构建快照再试**：`backups/releases/` 里按时间从新到旧，找上一份能通过启动的最小组合（代码 + 库）。如果只有代码坏，按 §4；只有库坏，按 §5。
5. **确认是不是环境问题**：端口被非 node 进程占用、磁盘满、权限不足、杀毒软件锁文件——这些都不是回滚能解决的。按 `报错预案.md` 对应条目先排除。
6. **数据库打不开时**：
   - 先只读打开（`--verify` 已经是只读）；如果 `integrity_check` 失败，说明这份备份也坏了；
   - 如果环境里装了 `sqlite3` 命令行，可以尝试 `sqlite3 <坏库> ".recover"` 导出到**新文件**，**绝不在原文件上操作**；本机是否安装 `sqlite3` **未核实**；
   - 不要用“删库重建”当默认动作。
7. **最后手段：空库启动**（数据丢失，必须用户明确同意）：
   ```powershell
   # 先把坏库和 WAL/SHM 全部改名保留，再允许建空库
   $env:AIDASH_ALLOW_EMPTY_DB = 'true'
   powershell -NoProfile -File .\60-deliver\scripts\deploy.ps1 -SkipBuild -KeepBackups 30
   ```
   主程序默认会在“库不见了但备份还在”时拒绝启动（`main.ts:256-284`、`70-operate/已知坑清单.md:24`）；`AIDASH_ALLOW_EMPTY_DB=true` 是显式绕过，**等于承认数据暂时找不回来**。启动后要立刻通知用户，并保留所有改名后的坏文件。
8. **升级给人**：发一张 AIDash `question` 卡或直接告诉用户，内容至少包含：失败到哪一步、试过哪些备份/快照、`integrity_check` 结果、丢失范围、当前服务状态。不要在没有证据的情况下给单一根因结论（`70-operate/故障记录模板.md` 要求至少两个候选）。
9. **不要静默继续**：回滚失败后如果服务能起来但数据可疑，宁可保持“只读观察/停机”，也不要让用户以为一切正常。

## 9. 回滚记录模板（最小字段）

| 字段 | 内容 |
|---|---|
| 回滚编号 | `RB-YYYYMMDD-序号` |
| 触发条件 | `R?` + 实际数值（例如“R2：5xx 8.3%，持续 12 分钟”） |
| 部署时间戳 | `deploy.ps1` 输出的 `<时间戳>` |
| 回滚类型 | 只代码 / 只数据 / 全量 |
| 使用的备份 | 文件名 + sha256 + `integrity_check` 结果 |
| 使用的构建快照 | `backups/releases/<时间戳>` |
| 数据丢失范围 | 备份时点之后创建的卡片/任务/审计（尽量列 ID 或数量） |
| 结果 | 成功 / 部分成功 / 失败 |
| 验证 | §7 清单逐条结果 |
| 后续 | 根因任务、补测试、改预案 |

## 10. 事实依据与未核实

| 结论 | 依据 |
|---|---|
| 备份用 SQLite Backup API、恢复前校验 sha256、恢复时旧库改名保留 | `30-design/设计文档包/05-数据库设计说明.md:859-893` |
| 迁移失败在单文件事务内回滚；checksum 不一致拒绝启动 | `migrate.ts:81-110` |
| 空库 + 有备份时默认拒绝启动 | `main.ts:256-284`、`startup.ts:49-74` |
| `/healthz` 返回 `db_path`、`/api/health` 返回审计链 | `app.ts:49-58`、`admin.ts:180-192` |
| `/api/metrics` 的 `cards_by_status` / `tasks_by_status` 是“状态→数量”的对象 | `admin.ts:83-91`、`admin.ts:194-210` |
| 访问日志含 status，可用于算 5xx 率 | `middleware.ts:93-110` |
| 重启 ≤10s、RPO/RTO 目标 | `20-spec/需求与验收判据文档.md:313`、`:316` |
| 迁移前备份命名 `pre-migrate-<from>-to-<to>-<stamp>.db` | `main.ts:298-303` |

**未核实项**：

1. 本方案没有在真实故障上演练过（当前没有真实故障输入；内部推进方案已移出公开仓，其中明确不编造假故障）。
2. 各触发条件的阈值是工程判断，不是实测统计得出的；首次真实回滚后应按实际数据校准。
3. `sqlite3 .recover` 是否可用取决于目标机器是否安装 sqlite3 CLI，本机未核实。
4. “备份时间点之后创建的卡片/任务”没有现成 API 过滤（已核实路由没有 `created_after`）；离线 SQL 查询是可选项，未在本机演练。
5. 30 分钟的数据回滚窗口是建议值，不是代码保证；实际可接受损失由用户决定。
