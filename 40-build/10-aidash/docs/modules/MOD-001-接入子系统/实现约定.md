# MOD-001 接入子系统 · 实现约定

> 本文件只写「怎么落地」。它与设计冲突时以设计为准，冲突本身记在《模块说明》的「已知偏差」。
> 本文件**不新增接口、不改字段、不替设计做决定**。

## 1 单元划分

| 文件 | 职责 |
|---|---|
| `src/server/http/app.ts` | 装配顺序：securityHeaders → requestId → accessLog → json → rateLimit → bearerAuth（只挂 `/api`、`/mcp`）→ 路由 → errorHandler → SPA 回退 |
| `src/server/http/middleware.ts` | 四个中间件；认证用 sha256 后 `timingSafeEqual` 比较 |
| `src/server/http/respond.ts` | 统一响应体 `{ok:true,data}` / `{ok:false,error:{code,message,retryable,details}}` |
| `src/server/http/routes/*.ts` | cards / tasks / channels / kb / memory / reports / admin 七组 REST |
| `src/server/mcp/index.ts` | 挂载 Streamable HTTP，每次 `tools/call` 刷新通道 `last_mcp_at` |
| `src/server/mcp/tools.ts` | MCP-001~023 的 zod schema 与调用转发（契约以 `tools/list` 为准） |
| `src/server/mcp/wait-cap.ts` | 把 MCP 等待上限压到 `mcp_wait_cap_seconds` |

## 2 线程与并发

单进程事件循环，没有工作线程。三处进程级状态都在内存：

- 限流桶：**令牌桶**，速率 `rate_limit_per_minute`（默认 300/分钟）+ 容量 `rate_limit_burst`（默认 60），只挂在 `/api` 与 `/mcp`，重启清零。当前只有单令牌认证，所以全进程一个桶，这正是 REQ-FN-028 的「每个令牌」；不按 IP，避免同机多 harness 互相拖累、也避免换 IP 绕过。将来引入多令牌时把单桶换成按令牌分桶即可。
- 有界等待者：由 `DecisionService` 的等待注册表持有，总数受 `max_waiting_requests` 限制，满了返回 `BUSY`；
- 请求 ID：`X-Request-Id` 透传，缺省时生成，贯穿日志与审计。

## 3 错误分支

| 触发 | 出口 |
|---|---|
| 缺 `Authorization` / 令牌不符 | `401 UNAUTHORIZED`，不提示「令牌错在哪」 |
| 超每分钟配额 | `429 RATE_LIMITED` + `Retry-After` |
| zod 校验失败 | `400 INVALID_ARGUMENT`，`details` 只给字段名与规则名 |
| 业务冲突（已认领、已作答等） | `409`，映射表见 `shared/errors.ts` 的 `HTTP_STATUS` |
| 未知异常 | `500 INTERNAL` + `INTERNAL_ERROR`，不把原始 message 透给调用方 |

## 5 边界

不在本模块做的事：业务状态判断、权限模型（当前只有 owner）、重试策略（由调用方按 `retryable` 决定）。
