## 1. 项目背景与目标

### 1.1 背景

V1 试图做一个“多工作台 Agent 调度总台”：公网总台负责接待、分解、派发、审批、汇总；异地工作台跑 Runner，把 CLI/HTTP/SSH/文件能力包成 Adapter。这个方向在评审中暴露了三类难以回避的问题：

1. **实时交互与长轮询错配**：终端会话、审批、任务状态都要求接近实时，但 Runner 只能出站长轮询。
2. **审批粒度与多轮执行冲突**：一次批准到底覆盖一个任务、一轮 attempt，还是单条命令，无法同时满足“单次点击”和“多轮改代码”。
3. **制品不在总台、审批人看不到**：总台只存引用，审批快照无法展示真实内容；代理下载又违反“总台不碰制品”的约束。

V2 的选择不是继续修补这三类问题，而是**换一个更小的产品形态**：

- 不再由 AIDash 调度其他主机，也不再把代码/工作区搬到 AIDash；
- AIDash 只做**用户看得到、需要用户决策**的那一层：卡片、任务树、决策、知识库建议；
- 具体干活的是用户已经在用的 **harness**（Claude Code、Codex、任意 CLI/IDE Agent），它通过 **MCP** 把“用户需要知道的事 / 需要转发的话术 / 需要澄清的问题”写进 AIDash；
- 其他主机的定时推进由独立的**值守壳 CLI**完成，AIDash 不管理它，只提供任务认领接口。

一句话：**AIDash 从“调度总台”退成“决策与沟通面板”，把执行留给 harness，把跨主机轮询留给值守壳。**

### 1.2 目标

- 用户打开一个网页，就能看到**按会话通道分组**的卡片流：哪些事需要知道、哪些话需要转发、哪些问题需要拍板。
- harness 在关键节点**主动发卡**，而不是把重要信息埋在终端日志里。
- 待澄清问题可以**有界阻塞** harness，用户回答后 harness 继续；超时则转异步，不把任务卡死。
- 任务树仍然保留：用户可以排任务、拖拽归并、复制节点、看状态；但**AIDash 不自动派发**，由 harness/值守壳认领。
- AIDash 可配置 **OKF 知识库路径**，在卡片上补充结合记忆与知识库的分析、建议、引用。
- 用户在网页上可以**批量推进决策**，不必逐张卡片点。
- 其他主机的定时任务由**跨平台值守壳**轮询推进，不占用 AIDash 的调度逻辑。

### 1.4 产品定义

#### 1.4.1 一句话

AIDash 是**一个人 + 多个 AI harness** 场景下的**决策与沟通面板**：agent 把“需要你知道 / 需要你转发 / 需要你拍板”的事写成卡片推进来；你排好的任务，由 harness 或值守壳自己认领执行。

#### 1.4.2 目标用户

| 是谁 | 典型处境 | 换到什么 |
|---|---|---|
| 独立开发者 / 小团队技术负责人 | 同时开 2~5 个 AI 编码会话，问题散落在多个终端 | 一个页面看完所有待拍板项，不用切窗口 |
| 用多台机器跑长任务的人 | 想让另一台机器接着干，却没有共同的“活单” | 任务树 + 认领租约 + 证据卡 |
| 需要事后留痕的人 | 复盘时要回答“当时为什么这么改” | 只追加审计 + 任务隐患标记 |

**非目标用户**：多人协作团队（V2 是单用户工具）、需要 AIDash 代为调度/派活的人、需要托管代码与制品的场景。

#### 1.4.3 核心闭环

```text
人排任务（Web） → harness / 值守壳认领 → 本地执行 → 发卡汇报或求助
      ↑                                                ↓
      └──────────── 人拍板 / 转发 / 调整 ←──────────────┘
```

四步都必须有落点，缺一步产品就不成立：

1. **排**：任务树支持父子层级、优先级、分类、暂缓与隐患标记。
2. **认**：`task.claim` 带租约；没人认领的任务不会假装“正在跑”。
3. **做**：执行发生在 harness 本地，AIDash 不碰代码、不碰工作区。
4. **证**：`complete` 前必须有挂到该任务的 status / artifact 卡，否则返回 `EVIDENCE_REQUIRED`。

#### 1.4.4 产品边界（与 §2.2 一致，这里只给结论）

- 不调度、不派活、不主动向任何机器推送任务；
- 不存代码、工作区、制品，产物只以链接或摘要卡呈现；
- 不持有第三方系统凭据，不做第三方数据摄入；
- 不做多用户、权限、计费、移动端。

#### 1.4.5 成功判据（设计目标，非实测值）

| 判据 | 目标 | 靠什么保证 |
|---|---|---|
| 待拍板项不丢 | 客户端超时前返回 `pending` + `card_id` | `card.ask` 的 25 秒主动返回 |
| 不阻塞执行 | 用户不在时 harness 能继续做别的 | 超时转异步，任务不被卡死 |
| 完成可追溯 | 每个 `done` 任务都有证据卡 | `complete` 前校验 `EVIDENCE_REQUIRED` |
| 复盘有依据 | 每个任务能查到隐患与决策记录 | `risk_note` 四列 + 卡片时间线 |
| 上手成本低 | 按 README「快速上手」可在本机跑起来 | 单一 SQLite、无外部服务依赖 |

## 2. 范围与边界

### 2.1 包含

- 一个 **AIDash 服务**：Web 界面 + MCP Server + REST API + SQLite + OKF 索引 + 可选的 LLM 增强。
- **会话通道**与**卡片**：信息卡、交接卡、决策卡、建议卡、状态卡、产物卡。
- **任务树**：单父层级、拖拽移动、复制、状态流转、任务与卡片关联。
- **决策推进**：单张回答、批量选择、超时默认动作、审计。
- **OKF 知识库接入**：可配置路径、frontmatter 校验、全文索引、引用展示。
- **AGENTS.md**：给任意 harness 的交互契约（MCP 用法、发卡规则、话术模板、任务规则、安全约束）。
- **值守壳 CLI**：跨平台、独立部署，轮询 AIDash 任务并驱动本地 harness。

### 2.2 明确不包含

1. **用户管理**：不提供注册、登录、角色、用户表、密码找回；AIDash 是单用户/单令牌工具。
2. **SMTP / 邮件 / IM 发送**：交接卡只生成“可复制的话术”，发送由用户自己做（邮件、微信等）。
3. **公开入口**：不提供匿名表单、公开 HTTP 提交、票据查询；外部反馈不再由 AIDash 接待。
4. **远程运维其他主机**：不提供终端会话、文件浏览/上传/下载、远程桌面。
5. **AIDash 自动派发任务**：不维护 Runner/Adapter/AgentCard，不主动连接其他主机；任务由 harness 或值守壳认领。
6. **自动从第三方系统摄入数据**：AIDash 不连接第三方系统、不持有其凭证、不做 IngestSource/Recipe/Item。
7. **多轮 attempt / 质量门禁编排**：由 harness 自己执行；AIDash 只记录任务状态与证据。
8. **工作区/制品中心**：AIDash 不存代码、不存工作区、不做 worktree；产物以链接或摘要卡呈现。
9. **多租户、计费、配额、移动端 App、模型训练**。
10. **团队协作**：V2 是单人工具；多人共享同一个 AIDash 不在范围内。

### 2.3 假设

- 用户主要在自己的电脑或可信内网使用 AIDash；默认只监听 `127.0.0.1`。
- harness 已经具备读写代码、执行命令、调用 MCP 的能力；AIDash 不负责安装或升级 harness。
- 值守壳运行在需要执行任务的第三方主机上，能访问 AIDash 的 HTTP/MCP 端点。
- OKF 知识库是本地目录，格式遵循 Google OKF v0.1（Wiki 文章带 `type/title/description/tags/timestamp` frontmatter）。
- 单实例规模：≤100 个会话通道、≤10,000 张卡片、≤1,000 个任务、≤10,000 篇知识库文档。

## 3. 角色与术语

### 3.1 角色

| 角色 | 说明 |
|---|---|
| 用户（Owner） | 唯一的决策者。通过浏览器看卡片、答问题、排任务；不区分管理员/普通用户 |
| Harness | 任意现成 AI 编码/执行工具（Claude Code、Codex 等）。通过 MCP 与 AIDash 交互，读 AGENTS.md |
| 值守壳（Watchdog） | 跨平台 CLI。轮询 AIDash 任务，启动本地 harness，回传状态；不被 AIDash 管理 |

### 3.2 术语

| 术语 | 定义 |
|---|---|
| AIDash | 本系统。单用户 AI 决策面板，提供 Web、MCP、REST、SQLite、OKF 索引与可选 LLM 增强 |
| 会话通道（Channel） | 一组卡片的归属容器。按 `channel_key` 唯一标识，例如 `host/project/topic`；不同 harness、不同项目、不同话题各自成通道 |
| 卡片（Card） | AIDash 的交互原子。类型：`info`、`handoff`、`question`、`suggestion`、`status`、`artifact` |
| 信息卡（Info） | “用户需要知道”的信息：结论、影响、证据、建议动作 |
| 交接卡（Handoff） | “需要转发给其他人”的沟通内容：收件人、渠道、原因、可直接复制的话术、截止时间 |
| 决策卡（Question） | “需要用户拍板”的问题：背景、选项、推荐、影响、截止时间、默认动作；可阻塞 harness |
| 建议卡（Suggestion） | AIDash 基于记忆 + OKF 知识库生成的分析与建议；必须带引用或标注“无知识库依据” |
| 状态卡（Status） | 任务状态变化、执行结果、失败原因、证据链接 |
| 产物卡（Artifact） | 指向代码提交、文件、日志、报告等外部产物的链接与摘要；AIDash 不存原件 |
| 任务（Task） | 任务树中的一个规划节点。单父层级；由用户或 harness 创建；由 harness/值守壳认领 |
| 认领（Claim） | 值守壳/harness 以租约方式占用一个任务，防止重复执行 |
| 租约（Lease） | 认领的有效期；到期未续租则任务回到可认领状态 |
| 值守壳（Watchdog） | 独立跨平台 CLI，循环“认领任务 → 调 harness → 回传 → 睡眠” |
| Harness 契约 | `40-build/10-aidash/AGENTS.md` + `40-build/10-aidash/skills/aidash-mcp/`（发布时复制到 harness 仓库根），定义 harness 如何使用 AIDash MCP |
| OKF | Google Open Knowledge Format v0.1。知识库文章用 YAML frontmatter 自描述类型 |
| MCP | Model Context Protocol。AIDash 通过 Streamable HTTP 暴露工具 |
| 有界阻塞 | `card.ask` 可以等待有限时间（默认 90s，最大 300s）；超时返回 pending，由 harness 轮询或继续其他工作 |

### 3.3 三个容易混淆的概念

| | 会话通道 | 卡片 | 任务 |
|---|---|---|---|
| 表达什么 | 这件事属于哪个上下文 | 用户此刻需要知道/转发/拍板什么 | 要做的活怎么拆、做到哪 |
| 基数 | 1 个通道多张卡片 | 1 张卡片属于 1 个通道 | 单父树，1 个任务 1 个父 |
| 谁创建 | harness 首次发卡时自动创建 | harness 或 AIDash（建议卡） | 用户或 harness |
| 谁推进 | 用户浏览/归档 | 用户阅读/回答/转发 | harness/值守壳认领并更新 |
| 关键约束 | `channel_key` 唯一 | 决策卡可阻塞；交接卡不自动发送 | AIDash 不自动派发；完成必须有证据 |

## 4. 功能需求与验收判据

> 编号说明：V2.0 **重新编号**，V1 的 REQ-FN-001~066 已归档，不再引用。每条需求都有唯一验收准则；第 7 节只给端到端验收，逐条对应关系以本节“验收准则ID”列为准。

### 4.1 会话与卡片

| 需求ID | 需求描述 | 来源 | 验收准则ID | 验收判据 |
|---|---|---|---|---|
| REQ-FN-001 | AIDash 应提供会话通道列表与卡片流：每个通道有唯一 `channel_key`、标题、所属 harness/项目；首次发卡时自动创建通道。 | 用户本轮“不同会话通道卡片呈现” | ACC-001 | 用 MCP 以 3 个不同 `channel_key` 各发 1 张卡 → Web 显示 3 个通道；用相同 key 再发 1 张 → 通道数仍为 3、卡片数 +1；卡片不会跨通道显示。 |
| REQ-FN-002 | 每张卡片必须属于且只属于一个通道，并声明一种类型：`info`、`handoff`、`question`、`suggestion`、`status`、`artifact`。 | 用户本轮 | ACC-002 | 六种类型各发 1 张 → 数据库 `channel_id` 均非空、`type` 正确；Web 按类型筛选结果正确；提交未知类型 → 400 `INVALID_ARGUMENT`。 |
| REQ-FN-003 | 信息卡应包含标题、正文（Markdown）、严重级别（`info`/`warn`/`critical`）、可选关联任务、可选链接；用户可标记已读/归档。 | 用户本轮“用户需知晓的重要信息” | ACC-003 | 发 1 张 `critical` 信息卡 → Web 置顶显示；标记已读后刷新仍为已读；归档后默认列表不显示，带 `include_archived=true` 可查。 |
| REQ-FN-004 | 交接卡应包含收件人、渠道（`email`/`wechat`/`other`）、转发原因、**可直接复制的话术**、截止时间、状态（`draft`/`copied`/`sent`/`ack`）；AIDash **不得自动发送**。 | 用户本轮“方便用户复制发邮件、微信” | ACC-004 | 发 1 张交接卡 → Web 显示“复制话术”按钮；复制内容与 `message_md` 逐字节一致；点击复制只把状态改为 `copied`，不产生任何网络发送；点击“标记已发送”后状态为 `sent`。 |
| REQ-FN-005 | 决策卡应包含背景、选项数组（每项含 `id`/`label`/`description`/`recommendation`）、是否允许自由文本、默认动作、截止时间、可选关联任务、是否阻塞。 | 用户本轮“待澄清问题带更多友好信息” | ACC-005 | 发 1 张含 3 个选项的决策卡 → Web 完整渲染背景/选项/推荐/影响/截止时间；回答选项 2 → 返回 `option_id=2`；允许自由文本时提交文本成功；无选项且不允许自由文本 → 400。 |
| REQ-FN-006 | `card.ask` 应支持**有界阻塞**：`wait_seconds` 取值 0~300；在等待期内被回答则直接返回答案；超时返回 `pending` + `card_id` + `poll_after_ms`。 | 用户本轮“阻塞调用 MCP” + 评审建议 | ACC-006 | 以 `wait_seconds=1` 提问且不回答 → 1~2s 内返回 `pending`；随后在 Web 回答，再调 `card.wait` → 返回 `answered`；`wait_seconds=0` → 立即 `pending`；`wait_seconds=301` → 400。 |
| REQ-FN-007 | 用户应能在 Web 上逐张回答决策卡，也能勾选多张后**批量推进**；批量操作必须先展示每张卡的选择摘要并要求二次确认。 | 用户本轮“按需批量推进决策” | ACC-007 | 勾选 5 张决策卡批量选择同一选项 → 二次确认后 5 张均为 `answered`；审计有 5 条单卡记录 + 1 条批量事件；若其中 1 张不允许该选项 → 整批拒绝并指出该卡。 |

| REQ-FN-009 | 所有写接口必须接受 `idempotency_key`；相同 key 的重复请求不得产生第二张卡/第二个任务，且应返回同一资源 ID。 | 分析员推断（防重放） | ACC-009 | 同一 `idempotency_key` 连续调用 3 次 → 数据库只有 1 行、3 次返回同一 ID；换 key 再调 → 2 行。 |

## 7. 需求追踪与端到端验收

### 7.1 逐条追踪

每条需求的验收准则已在第 4 节各表的“验收准则ID”列中一一对应；本仓库共 **64 条功能需求 / 64 条验收准则**（其中 5 条是明确的范围外条目），无未挂验收的需求。非功能需求见第 5 节，外部接口见第 6 节。

### 7.2 端到端验收 ACC-E2E

**目标**：一条脚本从空数据库开始，跑通“harness 发卡 → 用户决策 → 任务认领 → 值守壳执行 → 证据回传 → 知识库建议 → 审计完整”的主链路。

```
启动 AIDash（空库 + 测试 OKF 知识库）
  → mock harness 通过 MCP 注册
  → harness 发 1 张 info 卡（用户需知晓）
  → harness 发 1 张 handoff 卡（含可复制话术）
  → harness 发 1 张 question 卡（wait_seconds=2，阻塞）
  → 用户在 Web 回答该问题（选项 + 备注）
  → harness 收到 answered，继续
  → harness 创建任务 T1（draft），关联 question 卡
  → 用户在看板把 T1 拖到父任务下并确认 pending
  → 值守壳（mock harness）认领 T1 → in_progress
  → 值守壳发 1 张 status 卡 + 1 个 artifact 链接
  → 值守壳标记 T1 done（带证据）
  → AIDash 生成 1 条建议卡（引用 OKF 文档）
  → 用户采纳建议
  → 检查：4 类卡片可见、任务树正确、审计 ≥10 条、KB 引用可打开、无明文令牌
```

**通过条件**：
- 每一步状态可查；任一步失败整体失败。
- question 卡在用户回答前，harness 不得继续写操作。
- 任务 `done` 必须有证据卡或产物卡。
- 建议卡必须带 KB 引用或“无知识库依据”标注。
- 审计覆盖发卡、答题、任务创建/移动/认领/完成、建议采纳。

**存在理由**：V1 的反面案例是“模块验收全打勾、整条链路空转”。V2 必须用一条跨组件脚本证明“卡片 → 决策 → 任务 → 执行 → 证据”真的闭环。

- 其他主机的 harness 由独立跨平台值守壳轮询推进，不再由总台管理（用户本轮）。
- 保留任务树看板（用户本轮问答）。
- TypeScript 全栈（用户本轮问答）。

### 10.2 分析员推断（需用户核对，不同意即删除）

1. 单令牌、无用户体系的具体形态（Bearer token + token label）。
2. 卡片六种类型与各类型必填字段。
3. 决策卡有界等待 300s 上限与 24h 过期策略。
4. 任务完成必须有证据卡/产物卡。
5. 值守壳默认 60s 轮询、并发 1、租约 15min。
6. OKF 用 FTS5 而非向量检索。
7. 知识库只读、建议必须带引用/置信度。
8. 审计只追加、保留 2 年。
9. 卡片/任务/通道的容量与性能目标。

## 12. 认知对齐

### 12.1 我理解了什么

你要的不是一个“管所有机器人的总台”，而是一个**你能打开就看、看完就能拍板的 AI 面板**。执行由你已经在用的 harness 做；AIDash 只负责把“需要你知道的、需要你转发的、需要你决定的”变成卡片，并在你需要时结合 OKF 知识库给建议。任务树保留，但不再自动派发；其他主机的定时推进交给独立值守壳。

### 12.2 我的关键假设

- 你接受“单用户 + 单令牌”，不需要登录/角色/多租户。
- 你接受“交接卡不自动发送”，只生成可复制话术。
- 你接受“任务完成必须有证据”，否则会退回到“全打勾但链路空转”。
- 你接受“OKF 先做全文检索，不做向量检索”，V2.1 再升级。
- 你接受“值守壳是独立进程”，AIDash 不监控它的存活（只通过租约和心跳间接判断）。

### 12.3 我没有放进 V2 的内容及理由

| 内容 | 为什么不做 |
|---|---|
| 用户管理/登录/角色 | 单用户工具，增加的是运维与安全面，不是价值 |
| SMTP/IM 自动发送 | 交接卡只需要“可复制话术”；自动发送涉及凭证、模板、失败重试，收益低 |
| 公开入口 | 没有外部提出人场景；AIDash 不应暴露匿名面 |
| 远程终端/文件 | 与 harness 自带能力重复，且是最大安全面 |
| Runner/Adapter/AgentCard | 执行已交给现成 harness，AIDash 不再造执行层 |
| 自动派发/调度 | 值守壳认领即可；AIDash 主动连主机违反“极简 + 本地优先” |
| 第三方系统数据摄入 | 需要时由用户在 harness 里自行执行；AIDash 不碰凭证与轮询 |
| 多轮 attempt/门禁编排 | 由 harness 自己负责；AIDash 只记录结果与证据 |

### 12.4 需要你重点确认的三件事

1. **任务树的“完成证据”**：是否同意“没有证据卡/产物卡就不能标 done”？这会增加 harness 的回报动作，但能防止空转。
2. **决策卡过期**：是否同意“到期只标记 expired，不自动执行默认动作”？如果你希望“过期自动按推荐项执行”，需要明确授权。
3. **OKF 检索**：是否同意 V2 只做全文检索？如果你现在就要语义检索，需要增加嵌入模型与向量库的运维面。
